# service-runtime Specification

## Purpose
定义每个可部署服务的运行期契约：日志以什么格式、输出到哪里、按什么规则投递到集中日志系统，以及服务在容器中如何启动。目标是让所有可部署服务的排障面一致，而不是只有其中一个服务可被检索。

## Requirements

### Requirement: 日志格式包含追踪标识

每个服务输出的每一行日志 SHALL 使用统一格式，并包含足以把一次请求串联起来的追踪字段。

- 日志行 MUST 至少包含时间、线程名、级别、logger 名与消息正文。
- 当日志产生于一个追踪上下文内时，日志行 MUST 包含 `traceId` 与 `spanId`。
- 不在追踪上下文内时，MUST 以稳定的占位符表示缺失，不得省略该字段导致格式错位。
- 同一服务的所有输出目标（控制台、文件、集中日志）MUST 使用同一份格式定义。

#### Scenario: 跨服务日志可按 TraceID 串联
- **WHEN** 一次请求经网关进入系统服务并调用文件服务
- **THEN** 三个服务各自输出的日志行都带有同一个 `traceId`
- **AND** 每行的 `spanId` 对应各自产生的 span

#### Scenario: 无追踪上下文时格式仍对齐
- **WHEN** 服务启动阶段输出一条初始化日志
- **THEN** 该行仍然包含追踪字段位置，取值为占位符
- **AND** 不会因为缺少追踪字段而使后续字段错位

### Requirement: 日志按应用名落盘与滚动

开启文件输出时，每个服务 SHALL 在运行目录的 `logs/` 下写入以应用名命名的日志文件。

- 主日志文件 MUST 命名为 `<应用名>.log`，错误日志 MUST 命名为 `<应用名>-error.log`。
- 应用名 MUST 等于该服务的 `spring.application.name`，使文件名、注册名与指标标签一致。
- 错误日志 MUST 只包含 `ERROR` 级别记录。
- 文件 MUST 按大小与时间滚动，单个文件上限 MUST 可配置，保留窗口 MUST 可配置。
- 多个服务并存时，各自的文件 MUST NOT 相互覆盖。

#### Scenario: 启动后生成对应文件
- **WHEN** 以默认本地环境启动调度服务
- **THEN** `logs/iboot-job.log` 与 `logs/iboot-job-error.log` 被创建
- **AND** `iboot-job-error.log` 中不出现 `INFO` 级别记录

#### Scenario: 两个服务同时写日志
- **WHEN** 系统服务与通知服务同时运行并输出日志
- **THEN** 两个服务分别写入自己的文件
- **AND** 任一文件的内容不包含另一个服务的 logger

### Requirement: 结构化日志投递到集中日志系统

每个服务 SHALL 把日志以结构化形式投递到集中日志系统，使跨服务检索成为可能。

- 投递内容 MUST 为结构化记录，并携带标识来源服务的字段，其值 MUST 等于应用名。
- 投递 MUST 是旁路行为：集中日志系统不可用时，业务请求 MUST 仍然成功，服务 MUST NOT 因此启动失败。
- 投递必须使用有界缓冲，缓冲耗尽时 MUST 丢弃而不是阻塞调用线程。
- 集中日志系统恢复后，投递 MUST 自动恢复，无需重启服务。

#### Scenario: 集中日志系统不可用时业务不受影响
- **WHEN** 集中日志系统未启动
- **THEN** 服务正常启动并处理请求
- **AND** 请求延迟不因日志投递而显著增加

#### Scenario: 从集中日志系统区分来源服务
- **WHEN** 系统服务与通知服务同时向集中日志系统投递
- **THEN** 每条记录都能通过来源字段区分所属服务
- **AND** 可按该字段过滤出单个服务的全部日志

### Requirement: 输出目标在全部环境保持一致

每个服务 SHALL 在所有运行环境中输出到同一组目标，所有可部署服务之间的行为 MUST 一致。

- 控制台、主日志文件、错误日志文件与集中日志投递 MUST 在全部环境同时开启。
- 任一环境与任一服务 MUST NOT 缺少其中任一目标。
- 日志目录 MUST 可由环境变量覆盖，未覆盖时位于运行目录下的 `logs/`。
- 容器内 MUST 存在可写的日志目录，使文件输出不会因权限或路径缺失而失败。

#### Scenario: 本地与容器环境输出一致
- **WHEN** 分别以本地方式与容器方式启动任一服务并处理一次请求
- **THEN** 两种方式下控制台、主日志文件、错误日志文件与集中日志系统都能观察到该请求的日志

#### Scenario: 日志目录可覆盖
- **WHEN** 通过环境变量指定另一个日志目录
- **THEN** 文件输出落到该目录
- **AND** 目录不存在时服务给出明确错误而不是静默丢失日志

### Requirement: 容器启动契约

每个可部署服务 SHALL 以一致的脚本与镜像方式启动，使镜像构建不依赖对单个服务的特例处理。

- 每个可部署服务 MUST 提供启动脚本；镜像构建 MUST 使用统一模板，可以是一个共享的、按模块参数化的 Dockerfile，差异 MUST 仅限应用名、端口与 jar 文件名。
- 镜像 MUST 采用多阶段构建：构建阶段 MAY 执行完整的 Maven 构建，运行期镜像 MUST NOT 包含 Maven、JDK 编译器、构建缓存或项目源码。
- 运行期镜像 MUST 使用与构建阶段一致的 JDK 主版本。
- 镜像 MUST 以非 root 用户运行。
- 镜像内 MUST 存在一个可写的日志目录，使开启文件输出时启动不会失败。
- JVM 参数 MUST 可由环境变量覆盖，未覆盖时按容器可用内存推导。
- 镜像 MUST 声明服务监听的端口。

#### Scenario: 每个可部署服务都能构建镜像
- **WHEN** 在没有宿主机预构建 jar 的干净检出上构建任一可部署模块
- **THEN** 构建成功
- **AND** 镜像启动后健康检查返回 UP

#### Scenario: 运行期镜像不包含构建工具链
- **WHEN** 检查任一运行期镜像的内容
- **THEN** 镜像内不存在 Maven、`javac`、构建缓存或项目源码
- **AND** 镜像仅包含 JRE、该服务的 jar 与启动脚本

#### Scenario: 容器以非 root 运行
- **WHEN** 检查运行中的容器进程
- **THEN** 进程用户不是 root
- **AND** 开启文件输出时服务仍能写入日志目录

#### Scenario: JVM 参数可覆盖
- **WHEN** 启动容器时设置堆内存上限相关的环境变量
- **THEN** 进程的实际堆上限与设置一致
