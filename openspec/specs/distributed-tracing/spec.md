# distributed-tracing Specification

## Purpose

让一次用户请求跨越多个服务时可以被同一个标识完整串起来，使拆分后的故障定位与耗时分析不依赖逐服务翻日志。

## Requirements

### Requirement: 调用链上下文跨服务传播

一次请求 MUST 在整个调用链上共享同一个追踪标识；该标识在入口处产生（或沿用上游传入的值），并在每次跨服务调用时向下游传播。

- 上下文传播 MUST 使用业界通行的标准格式，使不同语言、不同框架的服务都能识别。
- 下游服务 MUST 沿用上游传入的追踪标识，不得在收到已携带标识的请求时另起一条新链路。
- 跨服务调用 MUST 同时传播父子关系，使链路能还原调用顺序，而不只是把事件堆在一起。

#### Scenario: 一次请求内标识一致
- **WHEN** 一次请求经过网关并调用两个后端服务
- **THEN** 该请求在三个进程中的追踪标识完全相同

#### Scenario: 已有标识时不再另起链路
- **WHEN** 请求进入某服务时已携带上游的追踪标识
- **THEN** 该服务产生的链路段挂在同一标识下，而不是新的标识

#### Scenario: 父子关系可还原
- **WHEN** 服务 A 调用服务 B
- **THEN** 链路中 B 的段表现为 A 段的子段

### Requirement: 链路可查询与可还原

追踪数据 MUST 被持久化到追踪后端，并能按追踪标识查询出完整链路。

- 查询结果 MUST 包含参与本次请求的全部服务，并标明每个服务在链路中的次序与耗时。
- 链路数据 MUST 至少保留到足以完成一次故障复盘的时间窗口。
- 每条链路 MUST 能定位到对应服务与接口，不需要额外的外部映射表。

#### Scenario: 按标识查到完整链路
- **WHEN** 用某次请求的追踪标识查询追踪后端
- **THEN** 结果包含该请求经过的全部服务
- **AND** 结果标明各段的耗时

#### Scenario: 链路可定位到接口
- **WHEN** 查看链路中的任意一段
- **THEN** 能看出它属于哪个服务的哪个接口

### Requirement: 日志与链路可关联

服务的日志 MUST 包含当前请求的追踪标识，使日志与链路可以互相跳转。

- 同一请求在多个服务产生的日志 MUST 带有同一个追踪标识。
- 未处于任何请求上下文中的日志 MUST NOT 伪造追踪标识。

#### Scenario: 跨服务日志可对齐
- **WHEN** 一次请求经过两个服务并各自产生日志
- **THEN** 两处日志带有相同的追踪标识
- **AND** 可用该标识把两处日志筛出来

#### Scenario: 后台任务不伪造标识
- **WHEN** 定时任务在没有请求上下文的线程中写日志
- **THEN** 日志不包含任何追踪标识

### Requirement: 采样可配置且追踪故障不影响业务

链路采样比例 MUST 可配置，并且追踪后端不可用时 MUST NOT 影响业务请求的成功与否。

- 系统 MUST 支持全量采样模式，供验收与排障使用。
- 默认采样比例 MUST 使本地环境产生的链路量可控。
- 追踪数据导出失败 MUST 只影响追踪数据本身，不得导致业务请求失败或明显变慢。

#### Scenario: 全量采样用于验收
- **WHEN** 采样比例被设为全量
- **THEN** 每一次请求都能在追踪后端查到对应链路

#### Scenario: 追踪后端不可用不影响业务
- **WHEN** 追踪后端停止运行
- **THEN** 业务请求仍正常返回
- **AND** 导出失败在日志中可见
