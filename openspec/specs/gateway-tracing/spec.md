# gateway-tracing Specification

## Purpose

让网关作为链路入口产生的服务端 span 可被稳定地验证与定位：一次用户请求在追踪系统里是一条完整链路而不是若干条互不相干的片段，并且判断"链路是否贯通"不依赖按时间范围检索追踪后端。

## Requirements

### Requirement: 转发请求产生服务端 span

网关 MUST 为每一个经路由转发的请求创建一条服务端 span。

- span MUST 携带请求方法与请求 URL，使链路上能看出这一段属于网关。
- span MUST 在请求结束后结束，且其耗时覆盖网关处理该请求的全过程。
- 该行为 MUST 由自动化测试守护，避免框架升级后在无人察觉的情况下消失。

#### Scenario: 转发请求出现在链路中
- **WHEN** 客户端经网关请求任一后端接口
- **THEN** 追踪系统里该请求存在一个属于网关的服务端 span
- **AND** 该 span 带有请求方法与请求 URL

#### Scenario: 观测创建被单元测试守护
- **WHEN** 观测注册表中没有任何属于该请求的服务端观测
- **THEN** 自动化测试失败，并打印实际捕获到的观测清单

### Requirement: 追踪上下文传递给下游

网关 MUST 把入口请求的追踪上下文传给下游服务，使下游产生同一 TraceID 下的子 span。

- 传递 MUST 使用业界通行的标准格式。
- 下游服务 MUST 沿用网关产生的 TraceID，不得另起一条链路。
- 网关自身产生的上游调用 span MUST 与入口 span 处于同一链路，父子关系正确。

#### Scenario: 多服务同链路
- **WHEN** 一次请求经网关调用后端服务，该服务再调用另一个服务
- **THEN** 追踪系统里各服务的 span 具有同一个 TraceID
- **AND** 父子关系为 网关入口 → 网关上游调用 → 下游服务

### Requirement: 不重复创建同级 span

网关 MUST NOT 为已有观测的请求再创建一条同级服务端 span。

- 健康检查、指标等运维端点的观测行为 MUST 保持与本变更之前一致。
- 转发请求 SHOULD 由框架既有的服务端观测覆盖，不得额外叠加自定义的同级观测。

#### Scenario: 运维端点不重复
- **WHEN** 请求指向运维端点
- **THEN** 该请求不因本变更而多出一条同级 span

#### Scenario: 转发请求不重复
- **WHEN** 请求经网关转发到后端
- **THEN** 该请求在网关侧只有一条服务端 span

### Requirement: 响应头回显追踪标识

网关 MUST 在响应头 `X-Trace-Id` 中回显本次请求的 TraceID（32 位小写十六进制）。

- 回显的标识 MUST 与追踪后端中该次请求的 TraceID 一致。
- 追踪被关闭时 MUST NOT 回显该响应头。
- 回显行为 MUST NOT 改变响应状态码与响应体。

#### Scenario: 无需查询追踪后端即可取得标识
- **WHEN** 客户端发起一次经网关的请求且追踪开启
- **THEN** 响应头包含 `X-Trace-Id`，其值为 32 位小写十六进制
- **AND** 用该值可以在追踪后端查到同一条链路

#### Scenario: 追踪关闭时不回显
- **WHEN** 追踪被关闭
- **THEN** 响应不包含 `X-Trace-Id`，且请求正常返回

### Requirement: 观测可整体关闭且故障不阻断请求

追踪 MUST 可整体关闭；与追踪相关的组件自身出错时 MUST NOT 使请求失败。

- 关闭后 MUST 不再产生网关 span，但转发行为不变。
- 响应头回显过程中的异常 MUST 被隔离，不得影响请求处理。

#### Scenario: 关闭追踪后业务不受影响
- **WHEN** 追踪被关闭
- **THEN** 请求正常返回，且不再产生网关 span

#### Scenario: 回显异常不影响请求
- **WHEN** 回显 TraceID 的过程发生异常
- **THEN** 请求仍然正常完成，状态码与响应体不变

### Requirement: 验证方式不依赖时间窗

对链路是否贯通的验证 MUST NOT 依赖按时间范围检索追踪后端。

- 验证 MUST 能从一个可复现的来源取得 TraceID（响应头或日志），再按该标识查询链路。
- 验证 MUST 在"查不到该标识"与"追踪后端不可用"两种情况之间给出不同结论。
- 验证 MUST 明确输出涉及的服务清单，以及缺失了哪些期望服务。

#### Scenario: 按标识验证多服务链路
- **WHEN** 执行链路验证并传入一个已存在的 TraceID
- **THEN** 脚本输出涉及的服务清单
- **AND** 在期望服务齐全时退出码为 0，缺失时退出码非零并指名缺失服务

#### Scenario: 不存在的标识给出明确结论
- **WHEN** 传入一个不存在的 TraceID
- **THEN** 脚本以非零退出码结束，并说明"追踪后端中没有该标识"，而不是静默通过
