# Design

## Context

两份文档的失真方式不同，处理方式也应不同。

**ROADMAP 的问题是「太多」，不是「太旧」。** 它同时承担了三个职责：路线规划、交付台账、决策记录。前两个与 `openspec/changes/archive/`（33 个归档变更）和 git 历史重复，只有第三个 —— 版本矩阵与决策理由 —— 是别处没有的。因此删除时要按「这是进度还是约束」逐段判定，而不是按「是否已完成」一刀切。

**README 的问题是「太旧」。** 它的技术栈、快速开始、目录结构、部署章节都停留在单体时代，与当前十个模块的实现不一致。它不是需要删减，而是需要按现状重写。

约束：

- 本次不改变任何代码与运行时行为，文档中每条断言都必须能在仓库里找到依据（`pom.xml`、`application.yml`、`Dockerfile`、`scripts/`）。
- 仓库里已经存在更细的文档（`doc/01`–`doc/23`、`openspec/specs/` 的 19 份能力契约），README 与 ROADMAP 只做入口与索引，不复制细节。

## Goals / Non-Goals

**Goals:**

- ROADMAP 收敛到约 200 行，读者能在一次滚动内看完「还没做什么」与「受什么约束」。
- 保留三条夹在已删除叙述里、但仍在约束未来决策的结论。
- README 成为可信的仓库入口：技术栈与 pom 一致，启动路径唯一，目录结构完整。
- 两份文档之间不产生新的重复：ROADMAP 管「未完成」，README 管「已具备」。

**Non-Goals:**

- 不整理 `doc/` 下的 23 份文档（它们各自在对应变更中维护，且 `doc/README.md` 已是导航）。
- 不新建「交付记录 / CHANGELOG」文档 —— 归档变更与 git 历史已经是记录。
- 不修改任何代码、配置、脚本或 Dockerfile。
- 不为 ROADMAP 已有的未完成项重新定优先级。

## Decisions

### D1 删除判定标准：进度 vs 约束

删除依据不是「已完成」，而是「它是否仍然约束未来的选择」。

| 内容类型 | 处置 | 例 |
|---|---|---|
| 交付过程叙述（谁在哪个变更里做了什么） | 删除 | §4.2 各服务的「变更 `add-x-service` 已交付」段落 |
| 已完成能力的细节 | 删除，压缩为一行进能力索引 | §1.2 的 18 行能力表 |
| 已消除的风险与已修正的偏差 | 删除 | §1.4 中打勾的缺口、§1.5 文档偏差 |
| 仍然生效的技术约束 | 保留 | §6.1 版本矩阵、§6.3 成本红线 |
| 仍影响未来决策的理由 | 保留 | §7 决策记录 |
| 未完成的路线 | 保留 | §4.3 阶段 3、§4.4 阶段 4 |
| 阶段 2 未达标的收尾项 | 保留并重写为一节 | Seata、Sentinel、RocketMQ、schema 改名、遗留表清理 |

替代方案「保留已完成内容但折叠（`<details>`）」被否决：折叠不减少行数，搜索与滚动仍然命中，等于没整理。

### D2 已完成内容不另建交付记录

`openspec/changes/archive/` 有 33 个归档变更，每个都带 proposal / design / tasks 与实现结果；git 历史记录了每一行改动。再写一份「交付记录」会产生第三份需要同步的副本。

ROADMAP 头部改为一句指引：已完成能力见能力索引与 README，变更历史见 `openspec/changes/archive/`。

### D3 能力索引与 README 功能清单的分工

两者都描述「已具备什么」，但视角不同，避免重复的边界如下：

- **ROADMAP 能力索引**：工程视角，一行一项，字段为「能力 → 一句话 → 归属服务 → 对应文档」。用于回答「这块能力在哪个服务里」。
- **README 功能清单**：用户视角，按服务分组，字段为「服务 → 用户可见功能」。用于回答「我能用它做什么」。

索引约 14 行，功能清单约 9 组。

### D4 三条抢救结论的安置

这三条原本夹在 §4.2 的交付叙述里，删除时必须显式搬运，否则会随段落一起消失：

| 结论 | 新位置 |
|---|---|
| 认证服务对公共客户端不签发刷新令牌，会话由共享会话滑动续期 | §7 决策记录，新增 7.5 |
| 系统服务是唯一「停掉会连带」的拆分，故障隔离判据为「失败有界」 | §7 决策记录，新增 7.6 |
| 跨 schema 只读是长期接受模式 | 保留在 §6 约束，指向 `doc/23` §11.12 |

```

1  目标与完成判据（原 §2）              ~20 行
2  能力一句话索引（新，承接 §1.2）      ~18 行
3  未完成路线

   3.2 阶段 3 云原生（原 §4.3）          ~12 行
   3.3 阶段 4 深水区（原 §4.4）          ~12 行
```

目标约 210 行。§3 原总览图中「阶段 0/1/2 已完成」的箭头链删除，改为只画阶段 3/4 的剩余路径。

### D6 README 目标结构

```
徽章与一句话定位
1  项目定位
2  架构总览       拓扑图 + 服务/端口表 + schema 表
3  技术栈         与 pom 逐条对齐
4  功能清单       按服务分组的用户可见功能
5  快速开始       dev-init.sh 为主 + 手工分步
6  目录结构       十个模块，一次，不重复
7  构建 / 测试 / 回归
8  镜像与部署现状 如实说明仅两份 Dockerfile，指向 ROADMAP 阶段 3
9  文档导航
10 License
```

长度目标 250–300 行。现有 527 行中重复的目录树、重复的功能段落、与实现不符的部署说明是主要压缩来源。

### D7 链接与断链

现有 README 里 `./doc/22-AI 工作台操作指南.md` 路径含空格，Markdown 会截断。统一改为尖括号写法 `[22-AI 工作台操作指南](<./doc/22-AI 工作台操作指南.md>)`，或改用 URL 编码的 `%20`。任务中安排一次全量链接检查。

### D8 `.env.example` 的服务地址

`IBOOT_JOB_SCOPE_URL` 仍指向 `http://iboot-admin`，该服务名在 `rename-admin-to-system` 后已不存在。同文件里 `IBOOT_AI_SCOPE_URL` 指向 `localhost:8080`，与「内部调用走 Nacos 服务名」的约定不一致 —— 本次只修正失效值，不改变地址策略（那属于后续的服务调用收口变更）。

## Risks / Trade-offs

- **删除误伤**：某段「已完成」里夹着仍然生效的结论 → 逐段复核表（附录 A）+ 三条抢救结论逐条确认落地。
- **文档再次漂移**：本次未建立防漂移机制（例如 CI 校验 pom 版本与 README 一致） → 接受；若后续需要，另起变更。
- **能力索引与功能清单边界模糊**：读者可能觉得两处都在列能力 → 用 D3 的字段差异区分（索引带归属与文档指针，功能清单带用户可见行为）。
- **ROADMAP 删除后无历史可查**：Git 保留完整旧版本，且 `openspec/changes/archive/` 覆盖每次交付 → 接受。

## Migration Plan

文档改动无部署与回滚成本：`git revert` 即可恢复原文档。建议一次性提交两份文档与 `.env.example` 修正，便于整体回滚。
