# Design

## Context

参见 `proposal.md` 的 Why。影响设计的现状事实：

- 资源服务器只有一个收口：`iboot-kernel` 的 `JwtAuthenticationFilter`，它校验 HMAC 签名后把**令牌原文当 Redis key** 取会话 Map，权限与角色都来自该 Map。`KernelSecurityAutoConfiguration` 只在宿主未自定义 `SecurityFilterChain` 时装配默认链，因此改造点集中且可一次生效于 admin / file / ai 三个资源服务。
- 会话实际语义是「闲置 30 分钟掉线」：`jwt.expiration` 虽是 7 天，但 Redis 键按 `session-timeout=30` 滑动续期，令牌只是入口凭证。
- 在线用户列表与强制下线（`OnlineUserApplicationService`）直接 `keys("login_tokens:*")` 扫描并解析会话 Map，强制下线即删除对应键。
- 网关按路径前缀分流，认证服务当前只承接三条 `/api/auth/*` 路径，`/api/auth/scope` 留在管理端。
- 服务间代理（AI → admin）只做 Bearer 透传，不解析令牌。
- Spring Authorization Server 自 Spring Security 7.0 起并入 Spring Security，Boot 4.0.3 BOM 已托管 starter。

## Goals / Non-Goals

**Goals:**

- 令牌自包含，资源服务器不依赖认证服务在线即可鉴权。
- 保住四项既有能力：独占会话、强制下线、在线用户列表、滑动续期。
- 用户可感知的会话生命周期与视觉体验不退化。
- 迁移过程分步可回滚，直到最后一步。

**Non-Goals:**

- 不引入 BFF（后端凭证代理）层。
- 不实现第三方身份源联邦登录、SAML、多租户。
- 不改动 `iboot-file` / `iboot-ai` 的业务逻辑与 43 个业务视图。
- 不改变 `/api/auth/scope` 的归属与契约。

## Decisions

### D1：授权服务器与认证服务同进程

授权服务器部署在 `iboot-auth` 内，与既有登录逻辑同进程。

**理由**：认证服务已经拥有凭据校验、用户目录、登录日志与共享 Redis；另起进程仍需要访问同样的资源，只会增加部署单元与密钥分发面。

**替代方案**：独立的 `iboot-oidc` 服务——隔离性没有实质收益，链路与运维成本翻倍，否决。

### D2：混合会话模型——令牌自包含 + Redis 撤销/在线名单

令牌携带 `sub`（用户 ID）、用户名、角色、权限、`jti`、`sid`；资源服务器验签后直接建立安全上下文。共享 Redis 中的 `login_tokens:<jti>` 同时承担两个职责：在线名单（供管理端查询）与撤销名单（键不存在即视为已失效）。

**理由**：纯无状态会丢失强制下线与在线列表；令牌内省（RFC 7662）会让认证服务重新变成每次请求的硬依赖。

**替代方案**：

- 纯无状态——功能倒退，否决。
- 内省端点——每请求一次网络调用，可用性耦合，否决。
- 短期令牌 + 不查任何存储——无法满足「强制下线立即生效」的验收场景，否决。

**代价**：每请求仍有一次 Redis 读取，与现状一致，不构成新增瓶颈。

### D3：请求鉴权的判定顺序

`JwtAuthenticationFilter` 改造为：

```
读 Authorization → 解析头部 alg/kid
  ├─ RS256：JWK 验签（公钥本地缓存，kid 未命中时回源刷新）
  │     → 校验 exp/nbf（容忍时钟偏移）
  │     → EXISTS login_tokens:<jti> ? 通过 : 401
  └─ HS256 且双栈开关开启：走旧路径（验签 + 读会话 Map），并在响应中标记令牌版本
```

双栈开关 `jwt.legacy-enabled` 默认开启、关闭后旧令牌校验整体移除。令牌版本过期时返回可区分错误码，前端据此静默重新登录而不是弹「密码错误」。

**理由**：单点改造，三个资源服务同时获得新能力；按 `alg` 分流不需要额外配置。

### D4：在线名单改用 `jti` 作为键后缀

`login_tokens:<jti>`、`online_token:<userId>` 的值改为 `jti`，不再存原始令牌。

**理由**：RS256 令牌长度约为原 HMAC 令牌的 4 倍，直接作为 Redis 键会显著放大扫描与网络开销；`jti` 同时是撤销判定的天然主键。

**影响**：`OnlineUserApplicationService` 的解析从「令牌后缀」改为「jti」，对外响应中的脱敏 `tokenId` 语义不变。窗口期内需要对两种后缀同时兼容，或在发布时接受一次在线列表清空（选择兼容，成本更低）。

### D5：前端作为公共客户端，授权码 + PKCE

门户是纯浏览器应用，采用公共客户端 + PKCE，不使用 client secret。**实测结论：Spring Authorization Server 7 对「公共客户端 + 授权码」组合不签发刷新令牌**（`OAuth2RefreshTokenGenerator` 中的 `isPublicClientForAuthorizationCodeGrant` 判定），因此不存在静默续期。

补偿方式：资源服务沿袭迁移前的语义——**只验签名与声明，过期时间由共享会话的滑动续期决定**，所以访问令牌有效期设为与会话超时相同的 30 分钟，只要会话还在滑动，用户就不会被踢出。前端不因令牌接近有效期而主动重新登录。

**替代方案**：BFF 模式——刷新令牌不落浏览器，安全性更高，但需要新增服务端会话层，与本轮「去掉服务端会话依赖」的方向相反，暂不采用。

### D6：多标签页不引入并发续期

由于公共客户端拿不到刷新令牌（见 D5），多标签页之间不存在「并发续期互相踢出」的问题，不需要单飞选举或服务端宽限窗口。前端仍保留「有刷新令牌才续期」的分支，作为将来改用 BFF 或机密客户端时的接口预留。

**理由**：这是 SAS 策略带来的简化，而不是功能缺失——会话生命周期由共享会话决定，与刷新令牌无关。

### D7：登录页由认证服务托管，复用品牌配置

认证服务提供自己的登录页（服务端渲染的静态页 + 轻量脚本），读取系统名称与主题变量渲染，滑块验证码迁移到该页面。

**替代方案**：

- 保留 SPA 登录页并用 BFF 代理——密码仍经过门户，且非标准流程，否决。
- 直接用框架默认登录页——无法满足品牌一致性要求，否决。

**代价**：滑块验证码是 Vue 组件，需要在认证服务侧重写；主题变量需要从门户样式包中复制一份最小子集。

### D8：客户端注册表放配置，不建库表

授权服务器登记的客户端（门户 Web、未来的第三方应用）写在 `application.yml` / Nacos 配置中，不新增数据表。

**理由**：不扩大认证服务对共享库的写边界（沿用既有过渡期约定），客户端数量少且变更低频。

**替代方案**：数据库版客户端仓库——在真正接入第三方应用之前没有收益，推迟。

### D9：网关注入新的认证前缀

网关新增 `/oauth2/**`、`/.well-known/**`、`/connect/**` 与认证服务登录页路径到认证服务路由，顺序排在 admin 兜底之前；白名单同步扩展。

### D10：认证服务自身的授权流程会话使用共享 Redis

授权码流程需要服务端保存授权请求状态。认证服务启用 Spring Session Redis 承载自身的 HTTP 会话，使其在多实例下仍然正确。

**理由**：否则认证服务一旦水平扩展，授权回调会因实例不匹配而随机失败。这里的状态与会话令牌是两回事，不违背 D2。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 短访问令牌 + 续期实现不当 → 用户频繁被踢出 | 把「活跃用户无感续期」做成端到端用例；刷新令牌同样按 `session-timeout` 滑动续期，保持闲置 30 分钟语义 |
| 多标签页并发刷新 → 复用检测误杀会话 | D6 的单飞 + 服务端宽限窗口；用两个浏览器上下文验证 |
| 认证服务多实例 → 授权回调随机失败 | D10 的共享会话；单实例部署时该风险为零 |
| 发布顺序错误 → 全站 401 | 先在 kernel 打开双栈并全量升级，再切前端，最后关闭旧校验；顺序写入迁移计划 |
| 在线名单键后缀改变 → 历史在线记录丢失 | 窗口期内同时兼容两种后缀 |
| 长连接（SSE / 下载）用查询参数传令牌，令牌变短后重连失败 | 重连前先刷新；网关保持原样转发查询参数（既有约束） |
| 登录页重写导致的品牌偏差 | 复用门户 CSS 变量与系统名称；把品牌一致性写入验收场景 |
| 双栈窗口被无限期拖延，旧 HS256 成为永久兼容负担 | 窗口由配置开关控制，并在 ROADMAP 登记关闭期限 |

## Migration Plan

分五步，前四步均可回滚：

1. **内核双栈**：`iboot-kernel` 同时支持 RS256 与 HS256，默认仍只走旧路径。三个资源服务升级后行为无变化。→ 回滚：回退版本。
2. **认证服务上线授权服务器**：新增标准端点，保留旧 `/api/auth/login`，网关放行新前缀。前端未切换。→ 回滚：关闭新路由与开关。
3. **前端切换**：登录改为跳转授权码流程，静默续期上线。→ 回滚：恢复旧登录页与直传接口。
4. **观察期**：一个发布周期内新旧令牌并存，验证在线用户、强制下线、闲置超时、多标签页。
5. **收敛**：关闭旧令牌签发与校验，移除旧登录接口，迁移登记改为 `done`。→ 不可回滚。

   **实际执行（2026-10-31）**：项目尚未对外发布，不存在需要保护的在线旧令牌，因此在第 4 步验收通过后直接收敛。
   只移除 `/api/auth/login`；`/api/auth/logout` 承担会话撤销、`/api/auth/register` 是功能本身，二者保留。

## Open Questions
