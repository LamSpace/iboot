# Spec Delta

## MODIFIED Requirements

### Requirement: 发起请假申请

系统 SHALL 允许拥有 `approval:apply` 权限的用户提交请假申请，申请必须包含请假类型、开始时间、结束时间、事由与审批人，申请人取自当前登录用户。

#### Scenario: 成功发起
- **WHEN** 已登录用户提交合法的请假申请，且审批人是启用状态的其它用户
- **THEN** 系统创建一条状态为「待审批」的申请记录，并启动一条指派给该审批人的审批流程
- **AND** 响应返回申请 ID、申请状态与提交时间

#### Scenario: 审批人不合法
- **WHEN** 审批人为空、不存在、已停用，或与申请人相同
- **THEN** 系统拒绝请求并返回明确的校验错误
- **AND** 不创建申请记录，也不启动流程

#### Scenario: 缺少权限
- **WHEN** 用户没有 `approval:apply` 权限
- **THEN** 系统返回 403，且不产生任何数据

#### Scenario: 用户目录不可用
- **WHEN** 审批人校验所依赖的用户目录不可用
- **THEN** 系统拒绝发起并返回明确错误
- **AND** 不创建申请记录，也不启动流程

## ADDED Requirements

### Requirement: 审批服务的独立启停与数据归属

审批能力 SHALL 由独立部署的服务提供，其可用性与数据归属 MUST 与其它业务功能隔离。

- 审批服务不可用时，管理端的用户、角色、菜单等其它功能 MUST 保持可用；对审批接口的请求 MUST 返回可辨识的失败，而不是无信息的错误。
- 审批业务表与流程引擎表 MUST 只由审批服务写入；其它服务 MUST NOT 直接写入这些表。
- 拆分 MUST NOT 改变审批的外部契约：路径、方法、响应结构与权限码保持原样。
- 管理端不可用时，审批服务 MUST 仍能完成已提交申请的查询与处理；通知登记失败 MUST NOT 阻断审批。

#### Scenario: 停掉审批服务

- **WHEN** 审批服务停止而管理端正常运行
- **THEN** 审批接口返回明确的不可用错误
- **AND** 用户、角色、菜单等管理端接口仍正常工作

#### Scenario: 停掉管理端

- **WHEN** 管理端停止而审批服务正常运行
- **THEN** 已登录用户仍可查询待办并完成审批
- **AND** 通知登记失败不影响审批结果

#### Scenario: 数据只由审批服务写入

- **WHEN** 检查审批业务表与流程引擎表的写入方
- **THEN** 只有审批服务写入这些表
- **AND** 其它服务即使跨库读取，也不产生写入

#### Scenario: 外部契约不变

- **WHEN** 对比拆分前后的接口基线
- **THEN** `/api/approval/**` 的路径、方法、响应结构与权限码完全一致
