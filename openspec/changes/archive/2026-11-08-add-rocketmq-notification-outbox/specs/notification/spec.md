# Spec Delta

## ADDED Requirements

### Requirement: 审批待办事件经可靠消息投递

系统 SHALL 在审批事务内把待办通知事件持久化到生产方 outbox，并在事务提交后异步投递到 RocketMQ。broker 或通知服务不可用时，审批提交 MUST 仍然成功；事件 MUST 在依赖恢复后自动补投，不得依赖进程内重试。同一事件的重投 MUST NOT 产生重复投递记录或重复站内消息。

#### Scenario: broker 不可用时审批仍然成功

- **WHEN** RocketMQ broker 不可用，申请人提交一条合法请假申请
- **THEN** 请假申请提交成功并可查询
- **AND** 通知事件保留在 outbox 中，状态为待发送
- **AND** broker 恢复后事件被自动投递，审批人收到通知

#### Scenario: 重复消息不产生重复投递

- **WHEN** 同一事件因重投被消费者处理多次
- **THEN** 同一事件、同一渠道、同一接收人只存在一条投递记录
- **AND** 站内消息不重复出现在消息中心

#### Scenario: 审批事务回滚不产生通知

- **WHEN** 审批提交过程中流程启动或申请落库失败
- **THEN** 申请与 outbox 事件一起回滚
- **AND** 不产生任何通知投递

#### Scenario: 事件可按稳定键检索

- **WHEN** 运维按事件 ID 查询消息
- **THEN** 消息键与 outbox 中的事件 ID 一致
- **AND** 可定位到对应的 broker 消息与投递记录

### Requirement: 通知事件消息契约

投递到 RocketMQ 的通知事件 MUST 包含事件 ID、事件类型、模板编码、接收人 ID 与模板参数。消息键 MUST 为事件 ID，消息标签 MUST 为事件类型；消费者 MUST 能仅凭消息体重建一次通知登记命令。

#### Scenario: 消费者重建登记命令

- **WHEN** 消费者收到一条审批待办事件消息
- **THEN** 消息体包含的事件 ID、事件类型、模板编码、接收人 ID 与参数完整
- **AND** 消费者据此登记与 HTTP 路径等价的投递记录

### Requirement: 消费失败与死信处理

消费者 SHALL 对瞬时失败返回失败结果，由 RocketMQ 按投递重试策略重试；超过最大重试次数后消息 MUST 进入 `%DLQ%<consumerGroup>`，并 MUST 可按消息键检索。可判定的永久性错误（模板停用、接收人不存在）SHALL 被记录并计入失败指标，MUST NOT 无限重试。

#### Scenario: 瞬时失败自动重试

- **WHEN** 消费者登记时数据库暂时不可用
- **THEN** 消息被重新投递并再次处理
- **AND** 数据库恢复后通知登记成功

#### Scenario: 超过重试上限进入死信

- **WHEN** 消息连续处理失败并超过最大重试次数
- **THEN** 消息进入消费者组的死信队列
- **AND** 运维可按事件 ID 检索到该死信消息

#### Scenario: 永久性错误不无限重试

- **WHEN** 消息指向的通知模板已停用
- **THEN** 消费失败被记录并计入指标
- **AND** 消息不被无限重投
- **AND** 审批记录与 outbox 事件不受影响

## MODIFIED Requirements

### Requirement: 通知触发与业务主流程解耦

业务主流程 MUST NOT 因通知登记或投递失败而失败。通知事件 SHALL 在业务事务内持久化到 outbox，投递 SHALL 在事务提交后异步执行；触发失败 MUST 可观测并可按退避重试，且重试 MUST NOT 产生重复投递。

- 请假申请提交成功与否，MUST 只取决于审批本身的合法性，不取决于通知模板、接收人渠道配置、通知服务或 broker 可用性。
- 通知登记失败（模板不存在或停用、接收人不存在）MUST 在消费侧记录明确错误并计入失败指标，但 MUST NOT 向提交方返回业务失败，也 MUST NOT 回滚已提交的申请或 outbox 事件。
- 通知服务或 broker 不可用时，事件 MUST 保留在 outbox 或 broker 中按退避重试；重试期间 MUST 保持事件 ID 稳定，使同一事件、同一渠道、同一接收人最多产生一条投递记录。
- 触发失败 MUST NOT 中断审批流程，也 MUST NOT 回滚已提交的申请。

#### Scenario: 模板停用不阻断审批提交

- **WHEN** `APPROVAL_TODO` 模板被停用，申请人提交一条合法请假申请
- **THEN** 请假申请提交成功并可查询
- **AND** 不产生任何渠道的投递记录
- **AND** 消费侧的失败被记录为可观测的错误与指标

#### Scenario: 通知服务不可用时审批仍然成功

- **WHEN** 通知服务或 RocketMQ broker 不可用，申请人提交一条合法请假申请
- **THEN** 请假申请提交成功
- **AND** 通知事件被保留并在依赖恢复后按退避重试
- **AND** 重试成功后，审批人收到与在线时一致的站内消息与外部渠道投递

#### Scenario: 重试不产生重复投递

- **WHEN** 同一次通知触发因失败被重试多次
- **THEN** 同一事件、同一渠道、同一接收人只存在一条投递记录
- **AND** 站内消息不重复出现在消息中心

#### Scenario: 通知正常时行为与拆分前一致

- **WHEN** 通知服务可用、模板启用、接收人渠道地址齐全
- **THEN** 审批人在站内、邮件、钉钉渠道收到与拆分前相同的通知内容
