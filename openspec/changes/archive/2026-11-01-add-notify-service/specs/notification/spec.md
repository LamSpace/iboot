# Spec Delta

## ADDED Requirements

### Requirement: 通知触发与业务主流程解耦

业务主流程 MUST NOT 因通知登记或投递失败而失败。通知触发 SHALL 在业务事务提交后执行；触发失败 MUST 可观测并可按退避重试，且重试 MUST NOT 产生重复投递。

- 请假申请提交成功与否，MUST 只取决于审批本身的合法性，不取决于通知模板、接收人渠道配置或通知服务可用性。
- 通知登记失败（模板不存在或停用、接收人不存在）MUST 记录明确错误并计入失败指标，但 MUST NOT 向提交方返回业务失败。
- 通知服务不可用时，触发 MUST 按退避重试；重试期间 MUST 保持事件 ID 稳定，使同一事件、同一渠道、同一接收人最多产生一条投递记录。
- 触发失败 MUST NOT 中断审批流程，也 MUST NOT 回滚已提交的申请。

#### Scenario: 模板停用不阻断审批提交

- **WHEN** `APPROVAL_TODO` 模板被停用，申请人提交一条合法请假申请
- **THEN** 请假申请提交成功并可查询
- **AND** 不产生任何渠道的投递记录
- **AND** 失败被记录为可观测的错误与指标

#### Scenario: 通知服务不可用时审批仍然成功

- **WHEN** 通知服务不可用，申请人提交一条合法请假申请
- **THEN** 请假申请提交成功
- **AND** 通知触发失败被记录并在服务恢复后按退避重试
- **AND** 重试成功后，审批人收到与在线时一致的站内消息与外部渠道投递

#### Scenario: 重试不产生重复投递

- **WHEN** 同一次通知触发因失败被重试多次
- **THEN** 同一事件、同一渠道、同一接收人只存在一条投递记录
- **AND** 站内消息不重复出现在消息中心

#### Scenario: 通知正常时行为与拆分前一致

- **WHEN** 通知服务可用、模板启用、接收人渠道地址齐全
- **THEN** 审批人在站内、邮件、钉钉渠道收到与拆分前相同的通知内容
