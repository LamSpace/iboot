# Proposal

## Why

`ROADMAP.md` 现有 713 行，其中约 500 行是已完成能力的叙述与逐次拆分的变更记录。这些内容与 `openspec/changes/archive/`（33 个归档变更）、`doc/` 下的操作指南以及 git 历史重复，导致「路线图」实际承担了「交付台账」的职责：读者要从一份 713 行的文档里自己分辨哪些还会发生。

`README.md` 则相反，它停留在单体时代的描述上：技术栈写着并不存在的 PostgreSQL，快速开始只教启动 `iboot-system`，项目结构缺了五个模块，部署章节声称支持容器化而实际只有两份 Dockerfile。作为仓库入口，它已经不能回答「这个项目现在是什么」。

两份文档一起失真，是阶段 2 拆分结束后最显眼的收尾欠账。

## What Changes

- **ROADMAP 瘦身**：从 713 行收敛到约 200 行，只保留「还没做的」与「仍然生效的约束」。
  - 删除：§1.1–1.3 现状盘点、§1.4 中已补齐的缺口行、§1.5 文档偏差记录、§4.0 阶段 0 全部、§4.1 阶段 1 全部、§4.2 中逐次拆分的交付叙述、§5 旧 TODO 17 项去向。
  - 保留并重组：§2 目标与完成判据、§6.1 版本矩阵、§6.3 成本红线、§7 决策记录。
  - 保留但改写：§4.2 中仍**未完成**的收尾项（Seata、Sentinel 业务接入、RocketMQ、`iboot_admin` 改名、遗留表清理）收敛为「阶段 2 收尾清单」。
  - 新增：一张约 14 行的「能力一句话索引」，承接原 §1.2 的能力全景，每项一行，指向对应服务与文档。
- **抽取三条仍然约束未来的结论**（它们夹在已删除的交付叙述里，不能随之消失）：
  1. 认证服务对公共客户端不签发刷新令牌，会话语义由共享会话的滑动续期承担。
  2. 系统服务是唯一「停掉会连带」的拆分，其故障隔离判据为「失败有界」。
  3. 跨 schema 只读是长期接受模式（`doc/23` §11.12）。
- **README 重写**：结构改为「项目定位 → 架构总览（拓扑图 + 服务/端口/schema 三张表）→ 技术栈 → 功能清单 → 快速开始 → 目录结构 → 构建测试与回归 → 镜像与部署现状 → 文档导航 → License」。
  - 技术栈与 `pom.xml` 逐条对齐，删除 PostgreSQL 等不存在的条目。
  - 快速开始改为以 `scripts/dev-init.sh` 为主路径，前端命令统一为 cnpm。
  - 目录结构补齐十个模块，删除重复的第二份目录树。
  - 部署章节如实说明「仅 `iboot-system` 与 `iboot-portal` 有 Dockerfile」，指向 ROADMAP 阶段 3。
- **修正 `.env.example`**：`IBOOT_JOB_SCOPE_URL` 仍指向已不存在的 `http://iboot-admin`。
- 本次**不改变**任何代码、构建、部署与运行时行为。

## Capabilities

### New Capabilities

无。本次是纯文档整理，不引入新的能力契约。

### Modified Capabilities

无。所有能力的行为、接口、数据归属均不变，因此没有 spec delta。

> 本变更在 `.openspec.yaml` 中设置 `skip_specs: true`。

## Impact

- `ROADMAP.md`：重写。
- `README.md`：重写。
- `.env.example`：修正一行失效的服务地址。
- 不涉及 Java 代码、Maven 构建、Docker 配置、数据库或前端。
- 风险集中在「删除时误伤仍然生效的约束」，因此设计阶段需要给出逐段的保留/删除判定表，任务阶段需要一条「删除清单逐项复核」的验收动作。
