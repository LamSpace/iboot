# Spec Delta

## REMOVED Requirements

### Requirement: 审计日志的统一写入目标

**Reason**: 数据库合并为单一 schema 后，「跨 schema 写入」与「所有权切换窗口」不再存在；原需求把物理边界写进了行为契约。

**Migration**: 由「审计日志的写入目标与一致性」承接，写入目标、旁路语义、失败可观测与结构所有权保持不变，只把边界从 schema 改为表。

## ADDED Requirements

### Requirement: 审计日志的写入目标与一致性

系统 SHALL 把带有 `@Log` 注解的操作记录写入一个可配置的审计表；该表由监控服务拥有并通过集中迁移管理，其他服务 MUST 在同一个数据库内写入。

- 写入目标 MUST 在服务启动时校验；非法目标 MUST 使启动失败，而不是在运行期写入未知表。
- 写入 MUST 是旁路行为：审计存储不可用时，业务请求 MUST 仍然成功。
- 写入失败 MUST 可观测：至少产生错误级日志，并使运维能从指标或日志判断该服务的审计记录正在丢失。
- 审计表的结构 MUST 只由拥有者定义；写入方 MUST NOT 创建或修改其结构。
- 写入方 MUST NOT 为审计表另建一张同名表，也 MUST NOT 在其它数据库中登记同名目标。

#### Scenario: 拆分服务写入共享审计表

- **WHEN** 拆分服务处理一个带 `@Log` 的请求
- **THEN** 审计表出现一条包含操作人、操作内容与结果的记录
- **AND** 记录与该服务的应用名可区分

#### Scenario: 非法写入目标导致启动失败

- **WHEN** 配置的审计表名不是合法的标识符
- **THEN** 服务启动失败并给出明确原因
- **AND** 不会以默认表名继续启动

#### Scenario: 审计存储不可用

- **WHEN** 审计表不可写
- **THEN** 业务请求仍然成功
- **AND** 日志中出现可定位的错误，且同一服务不会无限重复告警

#### Scenario: 所有写入方目标一致

- **WHEN** 检查全部服务的审计写入配置
- **THEN** 它们指向同一张由监控服务拥有的表
- **AND** 不存在按库名前缀区分的第二份审计目标
