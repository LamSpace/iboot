# 23 - 微服务底座操作指南

> 适用变更：`openspec/changes/add-microservice-foundation`
>
> 本文只覆盖**回归基线与网关**相关的操作。Nacos、链路追踪等章节在对应任务交付时补充。

## 1. 回归基线是什么

阶段 2 要把单体拆成多个服务。拆分最容易造成的三类损伤是：**接口路径漂移**、**权限判定变化**、**关键链路中断**。这三类问题都不会让编译失败，只会让用户在使用时撞见，因此需要一套能在拆分前后反复执行的检查。

`scripts/regress/` 提供四层检查：

| 脚本 | 检查内容 | 依赖 |
|---|---|---|
| `api-snapshot.sh` | 导出 8 个服务的 OpenAPI 并归一化为基线 | 服务已启动 |
| `path-conservation.sh` | 迁移前后全部路径并集守恒 | `golden/` 与 `migrations.txt` |
| `route-coverage.sh` | 每条接口路径都能被唯一路由规则解析 | `golden/` 与 `routes.txt` |
| `smoke.sh` | 关键链路端到端可用（登录、用户、文件、日志、SSE、通知、任务、备份、审批） | 全栈（中间件 + 9 个业务服务 + 网关） |
| `permission-matrix.sh` | 角色 × 接口 × 期望结果 | 全栈 |

`regress.sh` 是唯一入口，按「快照 → 路径守恒 → 路由覆盖 → 冒烟 → 权限矩阵」顺序执行，任一失败即非零退出。

## 2. 前置条件

1. 中间件、九个业务服务与网关已启动。推荐直接用一键脚本：

   ```bash
   scripts/dev-init.sh
   ```

   它会启动 mysql/redis/minio/es/nacos/tempo/sentinel-dashboard 与 RocketMQ，写入 Sentinel 基线规则，
   执行 `iboot-db-init`，再按顺序启动 monitor/system/auth/file/notify/job/workflow/ai/gateway，并等待健康。

2. 备份能力由 `iboot-job` 承担；`dev-init.sh` 默认导出 `IBOOT_BACKUP_ENABLED=true` 与开发密钥。
   单独启动 job 时需显式设置这两个变量，否则冒烟的备份链路会失败。

3. 数据库 `iboot` 与全部表结构由 `iboot-db-init` 创建（`scripts/dev-init.sh` 会自动执行）。

4. 默认账号 `admin / admin123456`，可用环境变量覆盖：

   | 变量 | 默认值 | 说明 |
   |---|---|---|
   | `REG_BASE` | `http://localhost:8080` | 管理端地址 |
   | `REG_AI_BASE` | `http://localhost:8081` | AI 服务地址 |
   | `REG_USER` | `admin` | 登录账号 |
   | `REG_PASS` | `admin123456` | 登录密码 |

## 3. 日常用法

```bash
# 与基线比对，有漂移即失败
bash scripts/regress/regress.sh

# 确认差异合理后，重新生成基线
bash scripts/regress/regress.sh --refresh
```

`--refresh` 会把当前导出结果写入 `scripts/regress/golden/`，并以它作为新的标准答案。**只在确认差异是预期的接口变更时使用**，否则等于把错误固化成基线。

CI 分层：PR 只跑 `route-coverage.sh`、全量构建与网关测试；定时/手动任务用 `dev-init.sh`
拉起全栈后执行 `regress.sh`。

## 4. 允许差异登记

接口发生变化时，按以下顺序处理：

1. 先判断差异是否属于本次变更的预期行为。路径、方法、必填参数、响应结构的变化一律视为**不允许**，除非本次变更明确就要改它。
2. 属于预期变化时，在变更说明中写清：改了哪条接口、为什么必须改、影响哪些调用方。
3. 执行 `--refresh` 刷新基线，并把新的 `golden/` 文件随代码一并提交。
4. 仅新增接口（不修改既有接口）时同样需要刷新基线，但在说明中单独列出新增项。

未登记的差异会让 `regress.sh` 失败，这是有意设计的——**沉默的漂移比显式的失败更贵**。

## 6. 已知约束

- **AI 服务的 `/v3/api-docs` 需要鉴权**，因此 `api-snapshot.sh` 会在设置了 `REG_TOKEN` 时附带令牌；`regress.sh` 会先登录再导出。
- **响应体被 CloudEvent 信封包裹**，分页接口还额外嵌套一层 `PageResult`（数据位于 `.data.data`），脚本中的 `jq` 表达式已按此编写。
- **数据权限依赖 SQL 别名**：`@DataScope` 上声明的别名必须与 mapper XML 中的表别名一致。新增带数据权限的查询时，若 XML 未起别名，会直接报 `Unknown column` 而不是静默失效——这是刻意保留的失败方式，便于立即发现。
- 权限矩阵会在库里创建并清理 `ROLE_SCOPE_TEST` / `regress_scope`；冒烟会保留一个 `regress_approver` 账号（审批人不能是本人，所以必须有第二个用户）。

## 7. 网关

### 7.1 端口与启动

| 项 | 值 |
|---|---|
| 端口 | `8088` |
| 启动 | `java -jar iboot-gateway/target/iboot-gateway-1.0.0.jar` |
| 健康检查 | `GET http://localhost:8088/actuator/health` |
| 路由查看 | `GET http://localhost:8088/actuator/gateway/routes`（仅 `local` 等已开启端点的 profile） |

### 7.2 Profile

| profile | 后端地址来源 | 用途 |
|---|---|---|
| `local`（默认） | `IBOOT_SYSTEM_URI` / `IBOOT_AI_URI` 静态地址 | 本地开发，不依赖注册中心 |
| `nacos` | 服务名 + 服务发现 | 接入注册中心后使用 |

`local` profile 的价值在于：注册中心没起来时仍能调通业务代码；排查线上问题时也可以用静态地址绕过注册中心。

### 7.3 路由表

按「具体前缀优先」排列，兜底放最后：

| order | id | 路径 | 目标 |
|---|---|---|---|
| 0 | `notify-sse` | `/api/push/**` | 通知服务（长连接，`response-timeout: -1`） |
| 10 | `ai` | `/api/ai/**` | AI 服务 |
| 20 | `file` | `/api/file/**` | 文件服务 |
| 25 | `notify` | `/api/message/**`、`/api/notice/**`、`/api/notification/**`、`/api/search` | 通知服务 |
| 26 | `workflow` | `/api/approval/**` | 审批工作流（见 §11.9） |
| 27 | `monitor` | `/api/log/**`、`/api/online/**`、`/api/monitor/{server,redis,minio}/**` | 监控与日志服务（按路径级登记，见 §11.10） |
| 28 | `job` | `/api/monitor/backup/**`、`/api/job/**` | 调度服务（备份按路径级登记，见 §11.8） |
| 30 | `auth` | `/api/auth/login`、`/api/auth/logout`、`/api/auth/register`、`/oauth2/**`、`/.well-known/**`、`/connect/**`、`/login` | 认证服务 |
| 100 | `system` | `/api/**` | 系统服务（兜底，见 §11.11） |

**每拆出一个服务，就在 system 兜底之前插入一条更具体的前缀。** 路由表是拆分的开关，也是回滚点。

### 7.4 跨域

跨域统一由网关处理（`spring.cloud.gateway.server.webflux.globalcors`），预检请求由网关直接应答、不转发到后端。后端服务不再各自维护跨域配置。

### 7.5 长连接推送

`/api/push/**` 单独成一条路由，并设置 `response-timeout: -1`：

- 不套用全局 10 秒响应超时，否则长连接会被定时切断；
- 查询参数中的凭证（`?t=token`）原样透传，网关不改写。

### 7.6 故障响应

上游不可用或超时不再返回无信息的 500，而是可区分的 JSON：

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 上游连接被拒 | `503` | `{"code":503,"message":"上游服务不可用","path":"..."}` |
| 上游响应超时 | `504` | `{"code":504,"message":"上游服务响应超时","path":"..."}` |
| 路由被限流 | `429` | `{"code":429,"message":"请求过于频繁","path":"..."}` |
| 其它未预期异常 | `500` | `{"code":500,"message":"网关内部错误","path":"..."}` |

单个服务故障只影响对应前缀：管理端不可用时 `/api/ai/**` 仍然正常。路由级限流以路由 ID
（`workflow`、`notify`）为 Sentinel 资源，规则存放在 Nacos 的 `iboot-gateway-flow-rules`，
调整后秒级生效；被限流只影响该路由，不影响其它路由。完整流程见 §13。

### 7.7 回滚

网关本身的回滚有两个层级，都不需要改业务代码：

1. **改回直连**：把 portal 的 Vite 代理与 nginx 目标从 `8088` 改回 `8080` / `8081`。
2. **路由回退**：把某个已迁移前缀的路由目标改回管理端，admin 旧实现保留一个发布周期。

### 7.8 测试

`iboot-gateway` 自带 6 个集成测试，用本地桩服务覆盖：兜底转发、具体前缀优先、推送通道转发、跨域预检、上游不可用降级、单点故障隔离。

```bash
mvn -pl iboot-gateway test
```

## 8. 注册中心与配置中心

### 8.1 服务名与端口

| 服务 | 注册名 | 端口 |
|---|---|---|
| 系统服务 | `iboot-system` | 8080 |
| AI 服务 | `iboot-ai` | 8081 |
| 文件服务 | `iboot-file` | 8082 |
| 认证服务 | `iboot-auth` | 8083 |
| 通知服务 | `iboot-notify` | 8084 |
| 调度服务 | `iboot-job` | 8085 |
| 审批工作流 | `iboot-workflow` | 8086 |
| 监控与日志 | `iboot-monitor` | 8087 |
| 网关 | `iboot-gateway` | 8088 |
| 运维控制台 | `iboot-ops` | 8089 |

注册名与各服务的 `spring.application.name` 一致，日志与指标中的服务标识因此统一。

### 8.2 配置接入

Nacos 3.x **不再支持 `bootstrap.yml`**，配置一律通过 `spring.config.import` 引入：

```yaml
spring:
  config:
    import: optional:nacos:iboot-system.yml
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:localhost:8848}
        enabled: ${IBOOT_NACOS_ENABLED:true}
        fail-fast: false
      config:
        server-addr: ${NACOS_ADDR:localhost:8848}
        file-extension: yml
        enabled: ${IBOOT_NACOS_ENABLED:true}
```

`optional:` 前缀保证配置中心不可用时仍能以本地配置启动。

### 8.3 注册中心故障时的行为

`spring.cloud.nacos.discovery.fail-fast` 默认值为 `true`，注册失败会让整个应用启动失败（实测 120 秒后崩溃）。本项目统一设为 `false`：

- 注册中心不可用时，管理端仍能在约 20 秒内启动并对外提供服务；
- 注册失败在日志中可见，不会静默；
- 注册中心恢复后，心跳任务会自动重新注册，无需人工重启。

### 8.4 网关的两种 profile

| profile | 转发方式 | 使用场景 |
|---|---|---|
| `local` | 静态地址 `http://localhost:8080` / `8081` | 注册中心未启动时开发 |
| `nacos` | `lb://iboot-system` / `lb://iboot-ai` | 正常联调与验证 |

切换：`java -jar iboot-gateway-*.jar --spring.profiles.active=nacos`

### 8.5 验证热更新

管理端的 `/actuator/env` 默认对值脱敏（显示 `******`），不能直接用来观察配置值。推荐用**有外部可观测行为**的配置项验证，例如备份开关：

```bash
# 1. 记录进程启动时间
curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/actuator/metrics/process.start.time

# 2. 经 Nacos 下发 iboot.backup.enabled=true，备份接口应成功
curl -X POST http://localhost:8848/nacos/v1/cs/configs \
  --data-urlencode dataId=iboot-system.yml --data-urlencode group=DEFAULT_GROUP \
  --data-urlencode "content=iboot:
  backup:
    enabled: true" --data-urlencode type=yaml

# 3. 再下发 false，备份接口应返回「备份功能未启用」
# 4. 两次启动时间相同，说明未重启
```

**注意**：环境变量优先级高于配置中心。若同时设置了 `IBOOT_BACKUP_ENABLED`，Nacos 里的值不会生效——验证热更新时不要设置同名环境变量。

### 8.6 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 容器起不来，日志提示 `NACOS_AUTH_TOKEN must be set` | Nacos 3.x 镜像即使关闭鉴权也要求令牌 | compose 已提供开发用令牌 |
| 控制台打不开 | Nacos 3.x 控制台与主端口分离 | 访问 `http://localhost:8849/`，不带 `/nacos` 前缀 |
| 服务启动失败，`ErrCode:-401 Client not connected` | `fail-fast` 为默认 true | 设为 `false` |

### 8.7 内部调用清单

服务之间的调用按注册中心服务名寻址、由调用方负载均衡，不经过网关。新增调用时按此表登记；
固定地址只允许作为启动期例外，且必须写明覆盖方式。

| 调用方 | 目标 | 用途 | 寻址方式 | 例外 |
|---|---|---|---|---|
| `iboot-file` | `iboot-system` | 数据权限范围 | 服务名 + 负载均衡 | 否 |
| `iboot-ai` | `iboot-system` | 数据权限范围、智能体工具 | 服务名 + 负载均衡 | 否 |
| `iboot-ai` | `iboot-job` | 备份状态查询与触发 | 服务名 + 负载均衡 | 否 |
| `iboot-job` | `iboot-system` | 任务列表的数据权限 | 服务名 + 负载均衡 | 否 |
| `iboot-monitor` | `iboot-system` | 日志列表的数据权限 | 服务名 + 负载均衡 | 否 |
| `iboot-workflow` | `iboot-notify` | 审批通知登记 | 服务名 + 负载均衡 | 否 |
| `iboot-workflow` | `iboot-system` | 审批通过扣减额度（携带 `TX_XID`） | 服务名 + 负载均衡 | 否 |
| `iboot-kernel` | `iboot-auth` | JWKS 公钥获取 | 固定地址，部署时覆盖 | **是** |

**JWKS 例外**：公钥获取发生在服务启动或首次验签时，此时调用方可能还没有完整的服务发现上下文；
同时负载均衡客户端会把任意主机名当作服务名，改用服务发现会使绝对地址覆盖失效。因此保持
`jwt.jwk-set-uri` 的默认值 `http://localhost:8083/oauth2/jwks`，部署时必须通过 `JWT_JWK_SET_URI`
指向可达地址。

## 9. 链路追踪

### 9.1 依赖与配置

Boot 4 把追踪自动配置拆成了独立 starter：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-opentelemetry</artifactId>
</dependency>
```

只加 `micrometer-tracing-bridge-otel` 不够——应用能启动，但不会导出任何 span。

配置（以管理端为例）：

```yaml
management:
  tracing:
    export:
      enabled: ${IBOOT_TRACING_ENABLED:true}      # 总开关
    sampling:
      probability: ${IBOOT_TRACING_SAMPLE:1.0}    # 采样比例（默认全采）
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: ${TEMPO_OTLP:http://localhost:4318/v1/traces}
  otlp:
    metrics:
      export:
        enabled: false                            # 指标仍走 Prometheus
```

> 属性名在 Boot 4 变更：旧的 `management.otlp.tracing.endpoint` 不再识别，必须用
> `management.opentelemetry.tracing.export.otlp.endpoint`。
>
> 总开关同样是新名字：`management.tracing.enabled` 在 Boot 4 已不起作用（能启动、不报错，
> 但追踪照常导出），必须用 `management.tracing.export.enabled`。这个坑很难从现象上看出来——
> 设了旧属性后行为毫无变化。
>
> 采样默认值从 `0.1` 调到了 `1.0`：0.1 会让"链路是否贯通"的验证变成概率事件，十次里九次
> 查不到。压测或生产按需用 `IBOOT_TRACING_SAMPLE` 调低。

### 9.2 跨服务传播的前提

出站 HTTP 必须使用 Boot 自动配置的 `RestClient`：

- 需要 `spring-boot-starter-restclient`（Boot 4 同样拆成了独立 starter）；
- 不要手写 `RestClient.builder()`，它没有观测能力，下游会另起一条链路；
- 手工构建时至少要挂 `ObservationRegistry`，否则同样不传播。

### 9.3 日志关联与检索

所有可部署服务使用同一份日志配置（内核共享，网关与运维控制台各单独一份等价配置），日志格式包含 `[traceId,spanId]`：

```
2026-10-31 00:32:00.079 [iBootScheduler_Worker-2] [,] DEBUG ...
2026-10-31 00:35:12.101 [tomcat-handler-5] [aff3fd1f8c3ec7a42143f28bc6a54488,d83d07f767d1268b] INFO ...
```

- 请求线程带标识；
- 定时任务等无请求上下文的线程显示 `[,]`，**不伪造标识**。

每个服务的日志同时落到三处：

| 目标 | 位置 | 用途 |
|---|---|---|
| 控制台 | 标准输出 | 本地与容器排障 |
| 文件 | `logs/<应用名>.log`、`logs/<应用名>-error.log` | 单机留存，按 100MB / 30 天滚动 |
| 集中日志 | Elasticsearch 索引 `iboot-logs-YYYY.MM.dd`，带 `app` 字段 | 跨服务检索 |

常用检索：

```bash
# 只看某个服务的日志
curl -s "http://localhost:9200/iboot-logs-*/_search?q=app:iboot-job&size=20" | jq '.hits.hits[]._source.message'

# 按 TraceID 串联一次请求
curl -s "http://localhost:9200/iboot-logs-*/_search?q=traceId:aff3fd1f8c3ec7a42143f28bc6a54488&size=50" \
  | jq '.hits.hits[]._source | {app, message}'
```

### 9.3.1 集中日志投递开关

日志先进入 Kafka 的 `iboot-logs` topic，再由 Logstash 写入 Elasticsearch。投递由两个属性控制，
默认值保证「不配置 = 关闭」，关闭时不创建生产者、不发起任何连接：

| 属性 | 环境变量 | 默认值 |
|---|---|---|
| `iboot.logging.kafka.enabled` | `IBOOT_LOGGING_KAFKA_ENABLED` | `false` |
| `iboot.logging.kafka.bootstrap-servers` | `IBOOT_LOGGING_KAFKA_BOOTSTRAP_SERVERS` | `localhost:29092` |

| 场景 | 做法 |
|---|---|
| 全栈 compose | 无需设置；`x-app-env` 已注入 `true` 与 `kafka:9092` |
| `dev-init.sh` 宿主机进程 | 不设置，落默认关闭；控制台与本地文件仍完整 |
| 宿主机需要集中日志 | `docker compose -f docker/docker-compose.yml up -d kafka kafka-init`，再带 `IBOOT_LOGGING_KAFKA_ENABLED=true` 与 `IBOOT_LOGGING_KAFKA_BOOTSTRAP_SERVERS=localhost:29092` 启动 |
| 自动化测试 | 不设置；需要真实验证的用例显式开启 |

模板见根目录 `.env.example`；Kafka 编排、主题保留期与停机演练见 §15。

### 9.4 查询链路

**首选：按标识查，不按时间窗查。**

网关会在响应头回显本次请求的 TraceID：

```bash
curl -s -D - -o /dev/null http://localhost:8088/api/user/list | grep -i x-trace-id
# X-Trace-Id: 112363636945bc0db5a37aa61c99e858
```

拿到标识后用脚本判断链路是否贯通：

```bash
# 判断链路里是否同时出现三个服务
bash scripts/regress/trace-chain.sh 112363636945bc0db5a37aa61c99e858 \
    --expect iboot-gateway,iboot-ai,iboot-system
```

输出会给出服务分布与父子关系，退出码：`0` 齐全、`1` 缺服务或没有该标识、`2` 参数错误、
`3` 追踪后端不可用。追踪后端按批次导出，脚本默认在 10 秒内按标识轮询（`--wait` 可调），
其余应用日志里的 `[traceId,spanId]` 也可作为标识来源。

**辅助：人工浏览。** Grafana → Explore → Tempo，按 TraceID 查询或按服务名浏览。直接调
Tempo API 时注意时间窗边界：

```bash
# 最近 10 分钟内的链路（仅用于浏览，不作验证依据）
NOW=$(date +%s)
curl -s "http://localhost:3200/api/search?start=$((NOW-600))&end=$NOW&limit=20"

# 单条链路详情
curl -s "http://localhost:3200/api/traces/<traceId>"
```

> 时间窗查询的 `end` 是排他的。一次"查不到任何网关 span"的误判就是这么来的：请求时间戳
> `…911.58` 落在 `end=…911` 之外。

### 9.5 网关侧的 span

网关对经路由转发的请求**会**创建并导出服务端 span，这是框架能力，不需要自己埋点：

```
iboot-gateway  http get      (SERVER，根)   method=GET, http.url=/api/user/list
  └─ iboot-gateway  HTTP GET (CLIENT)       spring.cloud.gateway.route.id=admin
       └─ iboot-ai  http get /api/ai/...    （下游服务）
            └─ iboot-system  http get /api/auth/scope
```

两点容易踩：

- 服务端 span 的低基数键 `uri` 是 `UNKNOWN`（网关没有 Spring MVC 那样的路径模板），路径只在
  高基数键 `http.url` 上，所以 span 名显示为 `http get` 而不是 `http get /api/user/list`；
- 不要自己再实现一个入口观测组件。框架已经在 `HttpWebHandlerAdapter` 里创建了服务端观测，
  重复创建会出现两条同级 span，污染父子结构与耗时统计。

`GatewayTracingTest` 用 `SimpleObservationRegistry` 断言"经网关的请求确实产生了服务端观测"，
它只读内存记录、不关心导出，因此能把"没创建"和"创建了但没导出"分开。

### 9.6 故障隔离与整体关闭

追踪后端停止时业务不受影响（实测请求仍返回 200），导出失败只在日志中记录。

需要彻底关闭追踪时设置 `IBOOT_TRACING_ENABLED=false`（落到 `management.tracing.export.enabled`）。
关闭后：不再产生 span，网关也不再回显 `X-Trace-Id`——那个标识在追踪后端查不到，回显它只会
把人引向错误方向。转发行为不变。

`GatewayTracingDisabledTest` 覆盖了这一点：关闭追踪时请求照常返回，且响应头中不含 `X-Trace-Id`。

## 10. 共享内核

### 10.1 模块与依赖

`iboot-kernel` 承载所有 HTTP 服务共用的三样东西：统一响应与异常处理、资源服务器鉴权、操作日志。

```xml
<dependency>
    <groupId>com.iboot</groupId>
    <artifactId>iboot-kernel</artifactId>
</dependency>
```

版本由父 POM 的 `dependencyManagement` 统一管理，各服务不需要写版本号。

| 包 | 内容 |
|---|---|
| `com.iboot.kernel.web` | `Result` / `PageResult` / `BusinessException` / `GlobalExceptionHandler` / `I18nUtil` |
| `com.iboot.kernel.security` | `JwtTokenUtil`、`JwtAuthenticationFilter`、`SecurityUtils`、白名单、`JwtSecurityConfig`、401/403 处理器 |
| `com.iboot.kernel.logging` | `@Log`、`LogAspect` 与 `sys_operate_log` 持久化链路 |

### 10.2 自动配置：不需要改启动类

宿主的组件扫描（通常是 `com.iboot.system`、`com.iboot.file`）覆盖不到 `com.iboot.kernel`，内核组件全部通过自动配置注册：

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  com.iboot.kernel.web.KernelWebAutoConfiguration
  com.iboot.kernel.security.KernelSecurityAutoConfiguration
```

**这一点必须记住**：如果自动配置没被加载，应用照样启动、接口照样返回 200，只是鉴权与异常处理没有生效——这是静默的安全失效，不是启动失败。`KernelSecurityAutoConfigurationTest` 断言了过滤器确实进入过滤链。

内核提供的每个 Bean 都带 `@ConditionalOnMissingBean`：

- 定义了自有 `SecurityFilterChain` 的服务（`iboot-system`、`iboot-ai`）保持原有过滤链，内核只提供过滤器与处理器；
- 新服务不写安全配置也能直接成为资源服务器。

### 10.3 白名单

白名单属于服务边界，由各服务自己声明：

```yaml
iboot:
  security:
    whitelist:
      - /actuator/**
      - /error
      - /v3/api-docs/**
```

内核只提供与业务无关的默认值（接口文档、`/actuator/**`、`/error`）。匹配语义：

- 以 `/**` 结尾 → 前缀匹配；
- 以扩展名通配符开头 → 后缀匹配（如 `/**/*.ico` 匹配任意 `.ico`）；
- 其余含 `*` → 通配符前的前缀匹配；
- 无通配符 → 精确匹配。

管理端与 AI 服务在 `application.yml` 里各自写全量列表，取值与迁移前的硬编码数组逐条一致。

### 10.4 全局异常处理的开关

内核默认注册 `GlobalExceptionHandler`（`Result` 信封 + 对应状态码）。如果服务已有自己的异常契约，用下面的配置关闭，避免既有响应结构被改写：

```yaml
iboot:
  kernel:
    exception-handler:
      enabled: false
```

`iboot-ai` 就是这种情形：它有自己的 `AiExceptionHandler`，关闭内核处理器后 OpenAPI 快照与迁移前完全一致。

### 10.5 401 / 403 约定

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 未携带令牌或被安全链拦截 | `401` | `Result` 信封，`message` 为「未授权，请先登录」 |
| 过滤器内异常（如 Redis 不可用） | `401` | `Result` 信封，`message` 为「认证失败，请重新登录」 |
| 已认证但无权限 | `403` | `Result` 信封，`message` 为「无权限访问」 |

内核不再依赖宿主的 `ObjectMapper`：响应体用 Jackson 3 的 `JsonMapper` 序列化，新服务不需要额外配置 Bean。

### 10.6 会话契约

鉴权的事实来源仍是共享 Redis，键与格式在 `Constants` 中定义：

| 键 | 内容 |
|---|---|
| `login_tokens:{token}` | 会话 Map：`userId`、`username`、`permissions` 等 |
| `online_tokens:{userId}` | 在线会话映射，用于单点互斥与在线用户列表 |

过滤器只读取与滑动续期，不签发令牌。续期时长取自 `jwt.session-timeout`（分钟）。

### 10.7 操作日志

内核只包含**写路径**：`@Log` 注解、`LogAspect`、异步 `OperateLogRecorder`（`JdbcTemplate` 插入 `sys_operate_log`，专用线程池 `operate-log-*`，写失败只告警）。

查询侧在 `iboot-monitor`：`OperateLogMapper.selectPage` 带 `@DataScope`，搬进内核会让多数服务携带一个静默失效的数据权限注解。

这是过渡形态：审计记录仍由内核直写目标表（现在是 `sys_operate_log`）。等 RocketMQ 接入后改为「发 CloudEvent → MQ → 落库」，届时删除内核中的直写实现；在那之前，直写是「服务停了不影响写入」的原因（见 §11.10 的验收记录）。

> 没有数据源的上下文里记录器只告警一次并跳过写入，不会阻断启动——这让非 Web 测试切片不受影响。

### 11.2 五个不会报错、但会静默出错的隐式契约

前三项是拆分 `iboot-file` 时实际踩到的，第四项是拆分 `iboot-auth` 时补上的，
第五项是修复操作审计写入路径时补上的，
**漏掉任何一项，服务都能启动、健康检查也通过**：

1. **会话 Redis 序列化**：资源服务器读的登录会话由管理端以 Jackson 序列化写入。若宿主使用 Boot 默认的 JDK 序列化模板，读出来是 `null`，表现为「令牌有效但一直 401」。内核已提供同序列化的 `redisTemplate` 默认 Bean（`KernelRedisAutoConfiguration`），定义了自有模板的服务会覆盖它。
2. **CloudEvent 响应信封**：`/api/**` 的 `Result` 响应必须包成 `{type, source, data}`，前端与回归脚本都按 `data.data` 取值。实现是 `CloudEventResponseBodyAdvice`，它的 `basePackages` 必须指向本服务的 controller 包，否则响应结构会少一层。
3. **API 版本策略**：控制器上的 `version = "1"` 需要 `ApiVersionConfig` 提供 `ApiVersionStrategy`，否则启动直接失败（`API version specified, but no ApiVersionStrategy configured`）。
4. **`jwt.secret` 必须逐字一致**：签发方与校验方共用同一密钥与同一会话键前缀。密钥写成不同值（哪怕只差一个字符）时，表现为「**登录接口返回 200 并给出令牌，但后续所有请求都是 401**」，日志里只有一行验签失败，很难联想到配置。新增服务时不要图省事改写默认值，直接用 `${JWT_SECRET:iboot-admin-secret-key-for-jwt-token-generation-minimum-256-bits}`。
5. **操作日志写入目标**：配置 `iboot.logging.operate-log-table: sys_operate_log`。表名格式非法时启动会失败；表不存在时启动日志会出现一条 `error`，但服务照常启动。审计表由监控服务拥有、由 `iboot-db-init` 建表，写入方只需对它有 `INSERT` 权限；改为内部写入接口或 MQ 留作后续变更。

### 11.4 文件列表的数据权限已修正

拆分时发现旧实现在 `sys_file` 上的数据权限是坏的：表没有 `dept_id` 列，DEPT 范围会直接 SQL 报错，SELF 范围按文件主键过滤。新服务改为 `LEFT JOIN sys_user u ON u.username = f.upload_by`，注解别名指向 `u`，并让统计查询同样应用过滤，保证分页总数与列表一致。权限矩阵新增了对应的受限用户用例。

### 11.5 `iboot-auth` 的临时状态

服务端口 **8083**，承载 `/api/auth/login`、`/api/auth/logout`、`/api/auth/register`。

| 项 | 现状 | 退出条件 |
|---|---|---|
| 数据库 | 与其余服务共用 `iboot`，数据源直连该库；不启用 Flyway | 长期接受：改为统一身份存储或系统服务内部写接口时收敛（见 §11.12） |
| 写操作 | 仅三类：`sys_user` 最后登录信息、注册插入 `sys_user`、插入 `sys_login_log` | 前两类是系统域唯一的写入例外，已在 §11.12 登记；登录日志属审计，见 §11.10 |

| 授权协议 | OAuth2 授权码 + PKCE，标准端点 `/oauth2/**`、`/.well-known/**`、`/connect/**`；登录页由本服务渲染 | 已完成 |
| 旧登录接口 | `/api/auth/login` 已移除；`/api/auth/logout`（撤销当前会话）与 `/api/auth/register`（自助注册）作为功能保留 | 已完成 |
| 授权记录 | 内存存储：重启后刷新令牌失效，需重新登录；已签发访问令牌的验签不受影响 | 需要跨重启续期时改为 Redis 存储 |
| `/api/auth/scope` | ❌ 不属本服务，由系统服务承载；它返回数据权限范围，属系统域 | 已完成（见 §11.11） |
| 登录指标 | `user_login_success` / `user_login_failed` / `user_online_count` 改由本服务上报，`application` 标签为 `iboot-auth` | 长期 |
| 管理端旧实现 | ✅ 已删除；网关把认证路径交给认证服务 | 已完成 |

**双栈过渡开关**：协议切换期间，资源服务同时接受两种令牌，由以下配置控制：

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `jwt.jwk-set-uri` | `http://localhost:8083/oauth2/jwks` | 认证服务公钥集地址。资源服务首次遇到自包含令牌时回源，之后本地缓存；认证服务短暂不可用不影响已缓存的验签 |
| `jwt.legacy-enabled` | `false` | 认证协议切换已完成，四个服务都关闭了旧令牌兼容；打开它只用于回滚演练 |

携带旧令牌的请求返回业务码 **`40101`**（令牌版本已过期），与普通认证失败（`401`）区分开——前端据此静默重新登录，而不是提示凭据错误。`/api/auth/login` 已随协议切换下线。

**一个容易被忽略的特性**：认证服务宕机时，**已登录用户不受影响**——资源服务器用已缓存的公钥验签，
只查共享 Redis 的撤销名单，不依赖认证服务在线；只有当用户尝试重新登录、或资源服务冷启动且公钥缓存为空时
才会失败。这条能力在协议切换后仍然保留。

### 11.6 认证服务的验收动作

```bash
# 1. OIDC 发现文档与公钥集
curl -sS http://localhost:8088/.well-known/openid-configuration | jq '{issuer, token_endpoint, jwks_uri}'
curl -sS http://localhost:8083/oauth2/jwks | jq '.keys | length'      # -> 1

# 2. 浏览器流程：未登录访问门户，应跳转到 http://localhost:8088/login 并回到原页面

# 3. 回归：脚本化授权码登录 + 全量用例（含登出后令牌失效）
bash scripts/regress/regress.sh

# 4. 链路追踪：一次登录应覆盖 gateway → auth
bash scripts/regress/trace-chain.sh <traceId> --expect iboot-gateway,iboot-auth

# 5. 故障隔离：停掉认证服务后，旧令牌仍可访问业务接口
#    kill $(cat logs/iboot-auth.pid)
#    curl -H "Authorization: Bearer <旧令牌>" http://localhost:8080/api/user/profile   -> 200
#    curl -X POST http://localhost:8088/api/auth/login ...                            -> 明确的 5xx/降级响应
```

> **构建注意**：只改 `iboot-kernel` 时，未改源码的依赖模块（file / ai）可能因为增量编译跳过打包，
> 仍带着旧的嵌套内核 jar 启动，表现为「admin 认新令牌、file/ai 返回 401」。遇到这种情况用
> `mvn -pl iboot-file,iboot-ai clean package -DskipTests` 重新打包再启动。

**Quartz 集群的注意事项**：

- 多个实例必须共用同一份 `QRTZ_*` 存储与同一个 `scheduler-name`（本服务为 `iBootScheduler`）；
- 节点之间的时钟偏移会影响触发精度，本地验证时用同一台机器即可；
- `QRTZ_LOCKS` 由 Quartz 自行维护，不要手工增删行；
- **故障语义是至少一次**：某个实例被强杀时，Quartz 会把该节点执行中的触发器恢复并重跑一次，
  故障瞬间可能出现两条同秒执行记录。任务实现必须幂等；实测 `sampleTask` 每 10 秒触发、
  双实例运行时正常时段每个时刻只有一条，强杀后出现一次重跑；
- 回退到单实例：把 `org.quartz.jobStore.isClustered` 改为 `false` 并重启即可，表结构无需变更。

**留在原处与已迁出的部分**

1. **自监控埋点**：`MonitorFilter`、`MonitoringInterceptor`、`BusinessMetricsService`、
   `DruidMetricsBinder`、`CustomHealthIndicator` 名字里带 monitor，但它们是每个服务对自身的埋点。
   搬进监控服务会让其它服务丢失 HTTP 耗时、业务指标与连接池指标，Grafana 面板会在无人察觉时变空。
   它们留在原服务（或未来的内核公共件），监控服务只实现读取侧。
2. **dashboard / statistics**：两者跨系统域与日志域聚合，留在系统服务；其中对日志的访问改为跨库
   读 `iboot_monitor` 的两张表，登记为长期接受（见 §11.12）。
3. **Druid 控制台**：仍是系统服务进程内的页面，`sys.druid.monitor.url` 的指向不变。
4. **Spring Boot Admin 已迁出**：由独立服务 `iboot-ops`（8089）提供，通过 Nacos 发现全部业务实例，
   业务服务不再配置 SBA client。`monitor.sba.url` 仍为 `/sba`：开发环境默认关闭控制台认证，
   由 Vite 代理到 8089；生产环境保持认证开启且只允许内网访问，公网网关不提供该路由。

**切换顺序（写侧切换的唯一正确顺序）**

1. 先让监控服务建好 schema（此时其它服务还没启动，写入目标仍指向旧表）；
2. 停止全部后端（`bash scripts/dev-init.sh --stop`），停机窗口开始；

4. 全仓确认写入目标已切换：`grep -rn "operate-log-table" --include=application.yml . | grep iboot_admin` 应无输出；
5. 启动 monitor，再启动其余服务（`bash scripts/dev-init.sh`）；

`iboot_monitor`，若它先于监控服务启动，启动校验会打出一条「目标表不可达」的 `error`

#### 11.11.1 为什么是改名，不是「新建 + 摘除」

前五次用「先 add 再 remove」是因为拆分期间源服务仍是回退点。这里路径与服务是一对一，
没有可切的流量，两步的中间态只是两个模块跑同一批路径。改名一次完成，回滚用 `git revert`。

#### 11.11.2 为什么 schema 不改名

依赖方有六个服务直连 `iboot_admin`，schema 改名必须在停机窗口内完成 dump/restore，
而 MySQL 没有 `RENAME DATABASE`。最容易翻车的一点是 **`flyway_schema_history` 必须随数据一起搬**：
漏掉它，改名后的服务会在空 schema 上重跑 `V1__initial_schema.sql`，而该脚本第一条就是
`DROP TABLE IF EXISTS sys_user`。此外 schema 里还躺着 25 张前几次拆分保留的遗留表，
清理它们与改名无法共用同一个窗口。

因此本次把 schema 名定义为历史名称，与模块名解耦。改名与清理另起变更，届时只有数据动作、
没有业务代码交织，回滚面更小。

### 11.12 同库表级只读契约

全部服务共用数据库 `iboot`。系统域的表被五个服务只读，系统服务自身也读监控服务拥有的审计表。
这条关系是**接受的长期模式**，不是待消除的临时债务，理由是：

1. 四个服务的 `DataScopeSqlBuilder` 把 `EXISTS (SELECT 1 FROM sys_user ...)` 直接拼进 SQL，
   改成远程调用不是替换一个客户端，而是重写数据权限的 SQL 合成方式；
2. 改成远程调用会让可用性倒退——现在系统服务挂掉，监控的日志列表仍然可用；
3. 共享库约束的是写入所有权，不是禁止读取。

代价是表与列事实上成了对外接口，因此把消费面写成契约并用测试锁定。

#### 11.12.1 规则

- 消费方 MUST 只读契约登记的表与列；读取未登记的表或列视为契约变更，需要同批发布。
- 消费方 MUST NOT 写入不属于它的表，唯一例外见 §11.12.3。
- 所有者删除或重命名被消费的列 MUST 视为破坏性变更。
- 所有者不可用时，消费方 MUST 返回明确错误，不得静默返回空集合或默认值。
- 表结构 MUST 只由 `iboot-db-init` 的迁移改变；服务 MUST NOT 在启动时执行任何 DDL。

#### 11.12.2 只读消费清单

| 消费方 | 表 | 列 | 用途 |
|---|---|---|---|
| `iboot-file` | `sys_config` | `config_key`、`config_value`、`deleted` | 上传大小上限、允许扩展名 |
| | `sys_dict_data` | `dict_type`、`dict_value`、`dict_label`、`deleted` | 导出时的字典标签 |
| | `sys_user` | `id`、`username`、`dept_id`、`deleted` | 文件列表的数据权限关联 |
| `iboot-job` | `sys_config` | `config_key`、`config_value`、`deleted` | 备份存储类型等参数 |
| | `sys_dict_data` | `dict_type`、`dict_value`、`dict_label`、`deleted` | 导出时的字典标签 |
| | `sys_user` | `id`、`dept_id`、`deleted` | 任务列表的数据权限关联 |
| `iboot-monitor` | `sys_config` | `config_key`、`config_value`、`deleted` | 监控阈值、运维控制台地址 |
| | `sys_dict_data` | `dict_type`、`dict_value`、`dict_label`、`deleted` | 监控状态与 Redis 分类的标签 |
| | `sys_dept` | `id`、`dept_name`、`deleted` | 在线会话的部门名 |
| | `sys_user` | `id`、`dept_id`、`deleted` | 日志列表的数据权限关联 |
| `iboot-notify` | `sys_config` | `config_key`、`config_value`、`deleted` | 消息与公告条数上限 |
| | `sys_dict_data` | `dict_type`、`dict_value`、`dict_label`、`deleted` | 标签解析 |

#### 11.12.3 写入例外

| 写入方 | 表 | 列 | 用途 | 收敛条件 |
|---|---|---|---|---|
| `iboot-auth` | `sys_user` | 注册时插入整行；登录时更新 `login_ip`、`login_time`、`deleted` | 自助注册与最后登录信息 | 引入统一身份存储或系统服务内部写接口时 |
| `iboot-auth` | `sys_login_log` | 整行 | 登录审计 | 属 `ops-monitoring` 的审计表归属约定，不属本契约 |
| 全部服务 | `sys_operate_log` | 整行 | 操作审计 | 由内核统一写入，属 `operation-logging` 的约定 |
| Seata 参与方 | `undo_log` | 整行 | AT 回滚日志 | 单库过渡形态；拆库后每个 schema 独立一张 |

#### 11.12.4 如何检查

```bash
# 用户表的写入应只有认证服务登记的例外
grep -rn "UPDATE sys_user\|INSERT INTO sys_user\|DELETE FROM sys_user" --include=*.java --include=*.xml iboot-*

# 结构变更只允许出现在 db-init 的迁移里
grep -rn "CREATE TABLE\|ALTER TABLE" --include=*.sql iboot-*/src/main/resources | grep -v iboot-db-init || echo "无越权 DDL"

# 列的变更：改动被消费的列时，先跑五个服务的单测
mvn -pl iboot-file,iboot-job,iboot-monitor,iboot-notify,iboot-workflow test
```

## 12. 拆分专用的三个回归脚本

`regress.sh` 的顺序是「快照 → 路径守恒 → 路由覆盖 → 冒烟 → 权限矩阵」。

### 12.1 `path-conservation.sh`

```bash
bash scripts/regress/path-conservation.sh
```

比较**本次导出**与**基线**的路径并集：并集必须完全相同；消失或新出现的路径必须能由 `migrations.txt` 解释。同时校验登记的迁移确实落地。

`migrations.txt` 每行四列：

```
<路径前缀> <源服务> <目标服务> <transitional|done>
```

- 服务名用快照名（`admin` / `ai` / `file` / `auth`），不是 Nacos 服务名；
- `transitional`：绞杀者过渡期，源服务仍保留旧实现，只要求目标服务已有该前缀；
- `done`：旧实现已删除，源服务再出现该前缀即失败。

`remove-file-from-admin` 把旧实现删掉后，把这条登记改成 `done`。

**登记粒度要按「真正搬走的边界」来定**。`extract-auth-service` 只搬了登录、登出与注册，
`GET /api/auth/scope` 仍留在管理端，所以不能登记 `/api/auth` 前缀——那样永远达不到 `done`：

```
/api/auth/login    admin auth done
/api/auth/logout   admin auth done
/api/auth/register admin auth done
```

对应的网关路由也必须是逐条路径，而不是 `/api/auth/**`，否则 scope 会被错误地转发到认证服务。

### 12.2 `equivalence.sh`

```bash
bash scripts/regress/equivalence.sh --record   # 迁移前，从 REG_BASE（默认 8080）录制
REG_RECORD_BASE=http://localhost:8082 \
  bash scripts/regress/equivalence.sh --record # 旧实现删除后，改从文件服务录制（登录仍走 REG_BASE）
bash scripts/regress/equivalence.sh --verify   # 迁移后，经 REG_GATEWAY（默认 8088）重放
```

覆盖四条只读请求：`list`、`{id}`、`download-url/{id}`、`export`。归一化规则：

- 业务 `timestamp` 与 CloudEvent 信封的 `id` / `time` 置为占位符；
- 预签名下载地址的查询串掩掉（带签名与过期时间）；
- Excel 只对工作表内容取哈希，忽略文档属性里的生成时间。

**适用范围仅限只读请求**：写操作的响应含自增 ID 与时间戳，由冒烟覆盖。录制与校验之间不能有写入，否则数据变化会被当成差异。

### 12.3 冒烟与矩阵的变化

- 冒烟的「文件上传与下载」整段改走网关，覆盖上传 → 列表 → 下载地址 → 下载内容 → 删除五步；
- 权限矩阵新增三条文件用例：无 `file:list` 时拒绝、有 `file:list` 时允许、仅本人数据范围下看不到他人文件（超管 7 个 vs 受限 0 个）。

**监控与日志拆分（`add-monitor-service`）新增的回归资产**

- `golden/monitor.json`：19 条路径的契约基线；`golden/monitor-equivalence.json`：5 条只读请求的等价基线；
- `migrations.txt` 新增 5 条 `transitional` 登记（按路径而不是 `/api/monitor` 前缀，否则会覆盖 job 的备份路径）；
- 冒烟新增「日志与在线会话」一段：登录日志列表、操作日志包含本次链路、在线人数，
  并把审计落库断言从 `iboot_admin` 改为 `iboot_monitor`；
- 权限矩阵新增监控域 4 项：无 `loginlog:list` 时拒绝、有权限时允许、本部门范围收紧、超管查在线人数；
- `equivalence.py` 新增 `monitor` profile：只覆盖操作日志列表/详情与三条非匹配过滤，
  登录日志与运行日志持续写入，不适合做等价基线。


## 13. Sentinel 治理

### 13.1 接入范围

| 服务 | 治理点 | Sentinel 资源 | 规则 data-id | rule-type |
|---|---|---|---|---|
| `iboot-gateway` | 路由级限流 | 路由 ID：`workflow`、`notify` | `iboot-gateway-flow-rules` | `flow` |
| `iboot-notify` | 内部通知端点入口流控 | `/internal/notifications` | `iboot-notify-flow-rules` | `flow` |

审批 → 通知已改为 outbox + RocketMQ，不再有 `iboot-workflow:notify-enqueue` 的调用方熔断规则；
内部端点仅保留一个发布周期作为滚动升级兼容层。

规则统一放在 Nacos 的 `SENTINEL_GROUP` 组，类型为 `json`。**Nacos 是唯一持久化来源**：
Sentinel Dashboard 上的规则修改只作用于运行期内存，服务重启或 Nacos 规则刷新后会回到基线；
需要长期生效的修改必须写 Nacos。

### 13.2 组件与启动

`dev-init.sh` 会把 `sentinel-dashboard` 与 Nacos、Tempo 一起拉起，并调用
`scripts/sentinel-init.sh` 写入基线规则；全栈 compose 部署由 `scripts/docker-deploy.sh`
在服务健康后执行同一脚本。Dashboard 地址：`http://localhost:8858`。

- 本地开发默认关闭 Dashboard 登录（compose 中 `auth.enabled=false`）；
- 非本地环境叠加 `docker/docker-compose.prod.yml`，必须提供
  `SENTINEL_DASHBOARD_USER` / `SENTINEL_DASHBOARD_PASSWORD`，缺失时 compose 直接失败；
- Dashboard 不经过网关、不嵌入门户，只允许本机或内网访问；
- 停 Dashboard 不影响业务请求、已加载规则与 Prometheus 指标。

### 13.3 规则维护与验收

写入或恢复基线规则：

```bash
# 幂等写入两个基线规则并回读校验
bash scripts/sentinel-init.sh --verify
```

临时下调网关 `notify` 路由阈值（验证 429 与单路由隔离）：

```bash
curl -s -X POST 'http://localhost:8848/nacos/v1/cs/configs' \
  --data-urlencode 'dataId=iboot-gateway-flow-rules' \
  --data-urlencode 'group=SENTINEL_GROUP' \
  --data-urlencode 'type=json' \
  --data-urlencode 'content=[{"resource":"notify","limitApp":"default","grade":1,"count":1,"strategy":0,"controlBehavior":0,"clusterMode":false}]'

for i in $(seq 1 20); do
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8088/api/message/list
done
# 预期：少量 401（带有效令牌时为 200），其余 429；/api/ai/** 不受影响
```

恢复基线：重新执行 `bash scripts/sentinel-init.sh`，或把对应 data-id 写成 `[]`。

通知链路已改为 outbox + RocketMQ，演练步骤见 §14.5。

指标验收：Prometheus job 为 `iboot-gateway`、`iboot-notify`；
触发一次限流后查询 `sum by (resource) (rate(sentinel_block_total[1m]))` 应非空。
Dashboard 与 Prometheus 的职责边界见 `docs/11` §11.7.2。

## 14. RocketMQ 可靠事件投递

### 14.1 链路与职责

```text
审批事务 ──写──> biz_notification_outbox
                      │
              OutboxRelay（FOR UPDATE SKIP LOCKED）
                      │ publish
                      ▼
            RocketMQ topic: iboot-notification
                      │ push
                      ▼
      iboot-notify consumer ──> sys_notification_delivery（既有渠道重试）
```

- `iboot-workflow`：审批事务内写 outbox，事务提交即代表事件已持久化；中继在短事务内抢占
  待发事件，事务外投递。成功标记 `SENT`，失败按指数退避回 `PENDING`，超过上限标记 `DEAD`。
- `iboot-notify`：`PushConsumer` 消费消息并复用既有 `NotificationApplicationService.enqueue`；
  登记侧唯一键 `uk_event_channel_recipient` 吸收重复消息。消费失败返回 `FAILURE`，由
  RocketMQ 重试，超过上限进入 `%DLQ%iboot-notify-consumer`。
- `/internal/notifications` 端点保留一个发布周期，仅供旧 workflow 实例滚动升级使用；新实例
  不再调用它。

### 14.2 组件与端口

| 组件 | 容器 | 端口 |
|---|---|---|
| NameServer | `iboot-rocketmq-namesrv` | 9876（容器内） |
| Broker | `iboot-rocketmq-broker` | 10911/10909（容器内） |
| Proxy | `iboot-rocketmq-proxy` | 8080/8081 → 宿主机 18080/18081 |
| Topic 初始化 | `iboot-rocketmq-init` | 一次性 |
| 存储属主初始化 | `iboot-rocketmq-store-init` | 一次性 |

- Topic：`iboot-notification`（4 读 4 写队列）。
- 消费者组：`iboot-notify-consumer`；死信队列：`%DLQ%iboot-notify-consumer`。
- Proxy 挂载 `docker/rocketmq/rmq-proxy.json`，其中 `useEndpointPortFromRequest=true` 让
  宿主机进程也能收到可访问的路由端点。
- `iboot-rocketmq-init` 执行 `docker/rocketmq/init-topics.sh`：Broker 端口可连时可能尚未完成
  NameServer 注册，此时 `mqadmin` 报错但退出码仍为 0；脚本按输出判断成功、最多重试 30 次，
  结束时校验 `topicRoute` 已注册，失败则以非 0 退出。

### 14.3 关键配置

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `iboot.rocketmq.endpoints` | `localhost:18081` | 宿主机进程使用；容器内由 compose 注入 `rocketmq-proxy:8081` |
| `iboot.rocketmq.ssl-enabled` | `false` | 本地明文 Proxy；云上 TLS 时开启 |
| `iboot.rocketmq.topic` | `iboot-notification` | 事件主题 |
| `iboot.rocketmq.consumer-group` | `iboot-notify-consumer` | notify 专用 |
| `iboot.rocketmq.consumer-enabled` | `true` | 关闭后消费者不再订阅 |
| `iboot.rocketmq.retry-interval` | `10s` | 订阅失败后的重试间隔 |
| `iboot.workflow.outbox.enabled` | `true` | 中继总开关；排空/回滚时置 `false` |
| `iboot.workflow.outbox.batch-size` | `20` | 每轮抢占数量 |
| `iboot.workflow.outbox.poll-interval` | `1s` | 轮询间隔 |
| `iboot.workflow.outbox.lease` | `5m` | `SENDING` 租约，超时重置 |
| `iboot.workflow.outbox.max-attempts` | `10` | 达到后标记 `DEAD` |
| `iboot.workflow.outbox.initial-backoff` | `5s` | 指数退避起点 |
| `iboot.workflow.outbox.retention` | `7d` | `SENT` 记录保留期 |

`dev-init.sh` 支持 `IBOOT_ROCKETMQ_ENABLED=false` 跳过 RocketMQ 中间件；应用仍能启动，
审批仍能提交，事件保留在 outbox。

### 14.4 运维命令

```bash
# 组件状态
docker compose -f docker/docker-compose.yml ps \
  rocketmq-namesrv rocketmq-broker rocketmq-proxy

# Topic 与路由
docker exec iboot-rocketmq-broker sh -c \
  'cd $ROCKETMQ_HOME/bin && sh mqadmin topicList -n rocketmq-namesrv:9876'
docker exec iboot-rocketmq-broker sh -c \
  'cd $ROCKETMQ_HOME/bin && sh mqadmin topicRoute -n rocketmq-namesrv:9876 -t iboot-notification'

# outbox 各状态数量
docker exec iboot-mysql mysql -uroot -proot iboot -e \
  "SELECT status, COUNT(*) FROM biz_notification_outbox GROUP BY status;"

# 按事件 ID 查死信（事件 ID 形如 approval-todo-<processInstanceId>）
docker exec iboot-rocketmq-broker sh -c \
  'cd $ROCKETMQ_HOME/bin && sh mqadmin queryMsgByKey \
   -n rocketmq-namesrv:9876 -t "%DLQ%iboot-notify-consumer" -k approval-todo-<processInstanceId>'
```

指标：

| 指标 | 服务 | 含义 |
|---|---|---|
| `notification_outbox_pending` | `iboot-workflow` | 待投递事件数 |
| `notification_outbox_sent_total` | `iboot-workflow` | 成功投递数 |
| `notification_outbox_retry_total` | `iboot-workflow` | 失败重排数 |
| `notification_outbox_dead_total` | `iboot-workflow` | 死信数 |
| `notification_consume_success_total` | `iboot-notify` | 消费成功数 |
| `notification_consume_failure_total` | `iboot-notify` | 消费失败数 |

积压告警建议：`sum(notification_outbox_pending) > 100` 持续 5 分钟，或
`increase(notification_outbox_dead_total[10m]) > 0`。

### 14.5 发布、演练与回滚

**发布顺序**：先执行 `V4__workflow_notification_outbox.sql`，再发布 `iboot-notify`（新增消费者，
保留内部端点），最后发布 `iboot-workflow`（outbox 生效，删除 HTTP 适配器）。

**broker 停机演练**：

```bash
# 1. 停 broker
docker compose -f docker/docker-compose.yml stop rocketmq-broker
# 2. 提交一条请假申请：审批成功，outbox 出现 PENDING
# 3. 恢复 broker
docker compose -f docker/docker-compose.yml start rocketmq-broker
# 4. 中继自动补投，outbox 变为 SENT，审批人收到通知
```

`notification_outbox_sent_total` 与 `notification_consume_success_total` 应同步增加。

**回滚**：先设置 `IBOOT_WORKFLOW_OUTBOX_ENABLED=false` 暂停中继并等待 `PENDING` 排空，再回滚
workflow；notify 消费者可保留，继续消费已发布消息。数据库表保留，不做收缩迁移。未排空的事件
需在新版本恢复后继续投递。

### 14.6 常见问题

| 现象 | 处理 |
|---|---|
| 客户端报路由端点为 `172.18.0.x:8081` | 确认 Proxy 挂载了 `useEndpointPortFromRequest=true`，并按宿主机 `18081` 连接 |
| 客户端连接被 TLS 拒绝 | 本地 Proxy 是明文端口，设置 `iboot.rocketmq.ssl-enabled=false` |
| 消费者启动失败，提示 topic 不存在 | 先运行 `rocketmq-init`；消费者也会在后台重试订阅，不阻塞服务启动 |
| broker 反复重启 | 检查 `rocketmq_broker_data` 卷属主；`rocketmq-store-init` 会 chown 到 uid 3000 |
| 审批成功但通知没到 | 查 `biz_notification_outbox` 状态与 `notification_outbox_*` 指标，再查死信队列 |

## 15. Kafka 日志管道

集中日志链路在服务与 Logstash 之间增加了一层 Kafka 缓冲，使 Logstash 重启或抖动期间日志
可在保留窗口内回放，而不是直接丢弃。开关与默认值见 §9.3.1，链路设计见
[11-可观测性设计 §11.5](./11-可观测性设计.md)。

### 15.1 链路与职责

```text
九个业务服务 + iboot-ops（logback: KafkaAppender）
        │ 非阻塞、有界缓冲、满则丢弃
        ▼
iboot-logs（KRaft 单节点，6 分区，保留 24 小时）
        │ 消费者组 iboot-logstash
        ▼
Logstash ──> Elasticsearch 索引 iboot-logs-YYYY.MM.dd ──> Kibana / iboot-monitor
```

- **Kafka 是缓冲，不是记录**：24 小时之外的日志不可回放；长期记录由 Elasticsearch 承担。
- **投递是旁路**：Kafka 不可用时业务请求照常成功，缓冲耗尽后日志被丢弃；恢复后自动续投，无需重启服务。
- **至少一次**：发送重试可能产生重复文档，ES 按天索引无唯一键，重复属于预期行为。
- **不是启动依赖**：任何服务都不 `depends_on: kafka`，Kafka 未就绪不阻止服务启动。

### 15.2 组件与端口

| 组件 | 容器 | 端口 |
|---|---|---|
| Kafka（KRaft，broker + controller） | `iboot-kafka` | 9092（容器内）/ 29092（宿主机） |
| Topic 初始化 | `iboot-kafka-init` | 一次性 |

- Topic：`iboot-logs`，6 分区，副本 1，`retention.ms=86400000`（24 小时），关闭自动建 topic。
- 消费者组：`iboot-logstash`；位点提交在 Kafka 的 `__consumer_offsets`。
- 双监听：`PLAINTEXT://kafka:9092` 给容器内服务，`PLAINTEXT_HOST://localhost:29092` 给宿主机
  进程与 `kafka-*.sh` 工具。健康检查调用 `kafka-broker-api-versions.sh`，反映 broker 是否可收发。
- `iboot-kafka-init` 执行 `docker/kafka/init-topics.sh`，`--if-not-exists` 保证重复执行幂等；
  已存在的 topic 不会被重建，也不会修改既有分区与保留期。

### 15.3 关键配置

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `iboot.logging.kafka.enabled` | `false` | compose 注入 `true`；宿主机与测试默认关闭 |
| `iboot.logging.kafka.bootstrap-servers` | `localhost:29092` | 容器内由 compose 注入 `kafka:9092` |
| topic / 客户端标识 | `iboot-logs` / 应用名 | 由三份 `logback-spring.xml` 固定 |
| 环形缓冲 | 8192 | 与改造前的 TCP appender 一致 |

appender 的内部参数（`KafkaAppender`）：`acks=1`、`max.block.ms=1000`、`request.timeout.ms=5000`、
`delivery.timeout.ms=30000`、`buffer.memory=32MB`、`linger.ms=0`、`compression.type=lz4`，
停机关闭生产者的等待上限 2 秒。

### 15.4 运维命令

```bash
KAFKA="docker exec iboot-kafka /opt/kafka/bin"
COMPOSE="docker compose -f docker/docker-compose.yml"

# 查看 topic 与保留期
$KAFKA/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic iboot-logs

# 查看消费组位点与积压（LAG 持续增长说明 Logstash 停机或消费过慢）
$KAFKA/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group iboot-logstash

# 抽样查看最近的消息
$KAFKA/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic iboot-logs \
  --from-beginning --max-messages 3

# 重复执行 topic 初始化（幂等）
$COMPOSE run --rm --no-deps kafka-init
```

### 15.5 演练与回滚

**停 Kafka（生产侧降级）**：

```bash
$COMPOSE stop kafka
# 持续发起业务请求：全部成功，延迟无明显变化；日志被丢弃
$COMPOSE start kafka
# 新日志在数秒内重新进入 ES，无需重启任何服务
```

**停 Logstash（消费侧回放）**：

```bash
$COMPOSE stop logstash
# 期间产生的日志留在 iboot-logs（最多 24 小时）
$COMPOSE start logstash
# 从已提交位点继续消费，日志补齐到 ES
```

**回滚**：revert「生产者切换」提交即恢复 TCP 直投（同时恢复 Logstash 的 tcp 输入）；
Kafka 容器与 topic 可保留，不影响回滚后的运行。回滚后需要重新部署服务镜像以载入旧配置。

### 15.6 常见问题

| 现象 | 处理 |
|---|---|
| 服务本地文件有日志，ES 里没有 | 先确认 `IBOOT_LOGGING_KAFKA_ENABLED=true`；再查 topic 是否有消息、`iboot-logstash` 的 LAG |
| ES 中出现重复日志 | 至少一次语义导致，属预期；按 `traceId` + `message` 去重查看 |
| Kafka 容器 unhealthy | 查 `docker logs iboot-kafka`；健康检查依赖 `kafka-broker-api-versions.sh` 可连 |
| 宿主机进程连不上 Kafka | 使用 `localhost:29092`，不要用 `kafka:9092`（后者只在编排网络内可解析） |
| 超过 24 小时的历史日志缺失 | 已超出 Kafka 保留期，不可回放；以 ES 中的索引为准 |
| 日志量骤降但服务正常 | 检查环形缓冲丢弃计数（Logback status）与 Kafka 可用性 |

## 16. Seata 分布式事务

### 16.1 定位与边界

审批通过在同一个 Seata AT 全局事务内完成三件事：

| 角色 | 服务 | 写入 |
|---|---|---|
| TM | `iboot-workflow` | 发起 `@GlobalTransactional("approve-leave")` |
| RM | `iboot-system` | `sys_user_leave_quota`、`sys_leave_quota_log` |
| RM | `iboot-workflow` | `biz_leave_application`、Flowable `ACT_*` / `ACT_HI_*` |

边界：

- 全局事务内只放纯 DB 写；通知仍由本地 outbox + RocketMQ 异步投递。
- 审批通过是 fail-closed：TC 或 system 不可用时审批失败，不静默跳过扣减。
- 驳回不扣额度，也不进入全局事务。
- 额度按 `user_id + year` 计次数，一次通过扣 1；默认值来自 `sys_config` 的
  `leave.quota.default-count`（缺失或非法按 10）。

### 16.2 组件与端口

| 组件 | 容器 | 端口 | 说明 |
|---|---|---|---|
| Seata Server | `iboot-seata-server` | 8091（TC） | file store，会话目录 `/seata-server/sessionStore`，named volume |
| Seata 控制台 | — | — | 2.5.0 镜像不提供 7091 控制台；排障用日志与业务表 |
| 内存 | — | — | `JVM_XMS=256m`、`JVM_XMX=512m`、`JVM_MaxDirectMemorySize=256m` |

`dev-init.sh` 把 seata-server 列入默认中间件，并在拉起 workflow/system 前等待 8091 可连。

### 16.3 关键配置

| 配置 | 默认值 | 说明 |
|---|---|---|
| `seata.enabled` | `true` | 参与方必须同时启用 |
| `seata.application-id` | `${spring.application.name}` | 事务分组内的应用标识 |
| `seata.tx-service-group` | `iboot_tx_group` | 与 `vgroup-mapping` 对应 |
| `seata.service.grouplist.default` | `${SEATA_SERVER_ADDR:localhost:8091}` | 容器内由 compose 注入 `seata-server:8091` |
| `seata.registry.type` / `seata.config.type` | `file` | 本地不依赖 Nacos 作为 Seata 注册/配置中心 |
| `iboot.leave-quota.internal-token` | 空 | 与 workflow 的 `IBOOT_SYSTEM_INTERNAL_TOKEN` 一致；缺失时内部端点 401 |
| `iboot.leave-quota.base-url` | `http://iboot-system` | workflow 调 system 的地址 |
| `IBOOT_SYSTEM_INTERNAL_TOKEN` | 本地默认 `iboot-dev-internal-token` | 由 `.env` 或 `dev-init.sh` 注入 |

### 16.4 XID 传播

- 客户端：workflow 的 `leaveQuotaRestClient` 注册 `SeataXidClientInterceptor`，`RootContext.getXID()` 非空时写 `TX_XID`。
- 服务端：system 与 workflow 注册 `JakartaSeataWebMvcConfigurer`，在 Controller 与本地事务开启前绑定 XID，请求结束后解绑。
- **虚拟线程**：`RootContext` 是普通 `ThreadLocal`；参与全局事务的调用链必须保持同步，不能切到 `@Async`、`CompletableFuture` 或 Reactor。
- **参与方未启用**：system 收到 `TX_XID` 但 `seata.enabled=false` 时返回 503，避免本地提交却不登记分支。
- **workflow 侧**：`HttpLeaveQuotaClient.deduct` 在 XID 为空时直接 503，避免审批在本地提交。

### 16.5 undo_log 与共享库

- 全部服务共用 `iboot`，因此只有一张 `undo_log`，由 `iboot-db-init` 的 V5 迁移创建；见 §11.12.3 写入例外。
- 成功提交后 Seata 异步清理 undo_log，通常数秒内清空；排障时用 `SELECT COUNT(*) FROM undo_log`。
- 两个服务自动代理得到相同的 `resourceId`（JDBC URL）。spike 实测 TC 仍按 `branchId` 分别提交/回滚；单库下由持有通道的 RM 读取共享 undo_log 执行回滚。
- 拆库后必须为每个服务设置唯一 resourceId，写法为 `new DataSourceProxy(dataSource, "<service-name>")` 并关闭自动数据源代理。

### 16.6 验收

```bash

```

覆盖：正常提交、额度不足、远程扣减后失败回滚、并发审批、内部扣减幂等、TC 不可用、system 不可用。回滚场景要求 workflow 以 `seata-demo` profile 启动：

```bash

```

### 16.7 AT 与 TCC 混用（Change 2 预告）

Seata 2.5.0 的 `ConnectionProxy.register()` 在全局事务中始终以 `BranchType.AT` 登记分支；`RootContext.inGlobalTransaction()` 只看 XID 是否存在。TCC 的 Try 如果走同一个被 Seata 代理的数据源，会同时产生 AT 分支，回滚时 TCC Cancel 与 AT undo 可能双倍补偿。

因此下一个变更（额度划转 TCC 实验）必须满足：

- TCC 动作使用**非代理数据源**；
- 全局事务内只有 TCC 分支，不与 AT 分支混用；
- 实现 Try/Confirm/Cancel 的幂等、空回滚与悬挂处理。

### 16.8 常见问题

| 现象 | 处理 |
|---|---|
| 审批返回 503「分布式事务协调器不可用」 | seata-server 未启动或 8091 不可达；`docker logs iboot-seata-server` |
| 审批返回 503「额度服务不可用」 | system 不可达或内部令牌不一致；检查 `IBOOT_SYSTEM_INTERNAL_TOKEN` |
| 审批返回 400「请假额度不足」 | 当年额度已用完；查 `sys_user_leave_quota` |
| undo_log 持续增长 | 有全局事务未完成；查 TC 日志与 `branch_table`（file store 无此表时看日志） |
| Druid 数据源未被代理 | 启动日志应有 `Auto proxy data source 'dataSource' by 'AT' mode`；没有则检查 Seata starter 与数据源 Bean |
| 回滚后额度未恢复 | 查 system 日志的 `BranchRollbackResponse` 与 `branch rollback success`；确认 undo_log 未提前清理 |
