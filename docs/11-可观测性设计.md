## 概述

### 11.1 可观测性三大支柱

iBoot 项目基于现代化的可观测性技术栈，提供完整的系统观测能力：

| 支柱 | 技术栈 | 用途 | 数据保留 |
|------|--------|------|----------|
| **Metrics（指标）** | Prometheus + Thanos + Grafana | 数值型监控数据，支持聚合计算和趋势分析 | 原始数据 30 天，5 分钟聚合 90 天，1 小时聚合 1 年 |
| **Logging（日志）** | ELK Stack（Elasticsearch + Logstash + Kibana） | 结构化日志收集、存储和检索 | 默认 30 天，可配置 |
| **Tracing（追踪）** | OpenTelemetry + Grafana Tempo | 分布式链路追踪，分析请求链路 | Tempo 本地磁盘，未配置保留期 |

链路追踪是并行的第三条数据流：

```
应用（各 iboot-* 服务，OpenTelemetry）
        │ OTLP/HTTP :4318
        ▼
     Tempo :3200
        │ 查询
        ▼
    Grafana :3000
```

- 应用侧由 `spring-boot-starter-opentelemetry` 产生 span，`management.opentelemetry.tracing.export.otlp.endpoint` 指向 Tempo。
- Tempo 接收后落本地磁盘；Grafana 的 `Tempo` 数据源指向 `http://tempo:3200`。
- 日志与 trace 通过 `traceId` 关联，详见「分布式追踪（Tracing）」章节。

### 11.5 数据流说明

**指标数据流（Metrics Pipeline）：**

1. **采集层**
   - iboot-system 应用通过 Micrometer 暴露 `/actuator/prometheus` 端点
   - Exporters 采集基础设施指标（MySQL、Redis、Node、Elasticsearch）
   - 采集频率：应用指标 10s，基础设施指标 15s

2. **传输层**
   - Prometheus 通过 Pull 模式定期抓取目标端点
   - 支持静态配置、文件服务发现、DNS 服务发现

3. **存储层**
   - Prometheus TSDB 存储近期数据（本地 24h）
   - Thanos Sidecar 实时上传数据块到 MinIO 对象存储
   - Thanos Store 从对象存储加载历史数据
   - Thanos Compact 执行数据压缩和降分辨率（30d 原始 → 90d 5m → 1y 1h）

4. **查询层**
   - Thanos Query 提供统一查询入口
   - 支持 PromQL 查询语言
   - 自动合并实时数据和历史数据

5. **展示层**
   - Grafana 连接 Thanos Query 作为数据源
   - 预配置监控仪表板
   - 支持自定义 PromQL 查询

**日志数据流（Logging Pipeline）：**

1. **采集层**
   - 所有可部署服务（含 `iboot-ops`）通过同一份 Logback 模板输出日志到 `logs/<应用名>.log` 与 `logs/<应用名>-error.log`
   - 同时把结构化 JSON 日志投递到 Kafka 的 `iboot-logs` topic，`app` 字段取自 `spring.application.name`
   - 投递是旁路行为：有界环形缓冲耗尽时丢弃而不是阻塞业务线程，Kafka 不可用不影响请求与启动

2. **传输层**
   - Kafka 以 KRaft 单节点运行，双监听 `kafka:9092`（容器内）与 `localhost:29092`（宿主机进程与 `kafka-*.sh` 工具）
   - Logstash 以消费者组 `iboot-logstash` 消费 `iboot-logs`，位点提交在 Kafka 的 `__consumer_offsets`
   - topic 保留期 24 小时，只作缓冲；超过窗口的日志不可回放，长期记录由 Elasticsearch 承担

3. **存储层**
   - Logstash 处理后写入 Elasticsearch
   - 按日期自动创建索引（`iboot-logs-YYYY.MM.dd`），可用 `app` 字段区分来源服务
   - 索引名与字段（`app`、`traceId`）在链路改造前后保持不变，`iboot-monitor` 的日志查询接口无需修改

4. **展示层**
   - Kibana 连接 Elasticsearch
   - 支持全文搜索、字段过滤、可视化图表

### 11.5.1 「每服务自监控埋点」与「监控服务读侧」是两件事

拆分后这两个概念很容易被混为一谈，混错的后果是**面板静默变空**，不会有任何报错。

| | 自监控埋点 | 监控服务读侧 |
|---|---|---|
| 归属 | 每个服务自己的进程内组件 | `iboot-monitor`（端口 8087） |
| 代表 | `MonitorFilter`、`MonitoringInterceptor`、`BusinessMetricsService`、`DruidMetricsBinder`、`CustomHealthIndicator` | `/api/log/**`、`/api/online/**`、`/api/monitor/{server,redis,minio}` |
| 作用 | 把本进程的 HTTP 耗时、业务指标、连接池指标暴露给 Prometheus | 读取审计表、共享 Redis、Elasticsearch 与中间件状态，供页面查询 |
| 缺失后果 | 该服务的 Grafana 面板无数据 | 日志页与会话页不可用 |

判定方法：问「它读的是谁的数据」。回答是「我自己进程的」→ 埋点，留在原服务（未来可下沉到内核）；
回答是「别人写的表或共享中间件」→ 属于监控服务。

也因此，`com.iboot.monitor.infrastructure.config` 里只应出现读取侧组件：
把 `DruidMetricsBinder` 之类搬进监控服务，会让管理端及其它服务丢失自己的连接池指标。

### 11.5.2 运维控制台：单实例巡检与运行期控制

`iboot-ops`（端口 8089）是独立于指标、日志、链路之外的第四个观测面。它通过 Nacos 的
`DiscoveryClient` 拉取全部 `iboot-*` 实例，聚合各实例的 Actuator 页面，**不承担**指标存储、
日志检索或链路分析。

| 工具 | 回答的问题 |
|---|---|
| Prometheus + Grafana | 过去一段时间错误率、P95、容量趋势 |
| ELK | 某个 TraceId 的日志与异常上下文 |
| Tempo | 一次请求跨了哪些服务 |
| `iboot-ops` | 这个实例现在堆怎么样、线程卡在哪、把某个 logger 调到 DEBUG、查看环境/配置/Bean/缓存/定时任务 |

业务服务不需要配置 SBA client；控制台侧通过 `spring.boot.admin.discovery.services=iboot-*`
限定发现范围，并忽略自身。开发环境从门户“服务器监控”页以同源 iframe 打开，生产环境只允许
内网访问，公网网关不提供 `/sba` 路由。控制台不可用不影响任何业务接口。

### 11.7 自定义业务指标

**BusinessMetricsService 实现：**

```java
@Service
@Slf4j
public class BusinessMetricsService {

    @Autowired
    private MeterRegistry meterRegistry;

    // 用户登录指标
    private Counter userLoginSuccessCounter;
    private Counter userLoginFailedCounter;
    private AtomicInteger onlineUserCount;

    // 业务流程指标
    private Timer businessProcessTimer;
    private Counter businessProcessSuccessCounter;
    private Counter businessProcessFailedCounter;

    // 缓存指标
    private Gauge cacheHitRateGauge;
    private AtomicInteger cacheHitCount;
    private AtomicInteger cacheTotalCount;

    // 文件操作指标
    private Counter fileUploadCounter;
    private Counter fileDownloadCounter;
    private DistributionSummary fileUploadSizeSummary;

    @PostConstruct
    public void init() {
        // 登录成功次数
        userLoginSuccessCounter = Counter.builder("user_login_success")
                .description("用户登录成功次数")
                .tag("application", "iboot-system")
                .register(meterRegistry);

        // 登录失败次数
        userLoginFailedCounter = Counter.builder("user_login_failed")
                .description("用户登录失败次数")
                .tag("application", "iboot-system")
                .register(meterRegistry);

        // 在线用户数（Gauge 实时值）
        onlineUserCount = new AtomicInteger(0);
        Gauge.builder("user_online_count", onlineUserCount, AtomicInteger::get)
                .description("在线用户数量")
                .tag("application", "iboot-system")
                .register(meterRegistry);

        // 业务流程处理耗时（Timer）
        businessProcessTimer = Timer.builder("business_process_duration")
                .description("业务流程处理耗时")
                .tag("application", "iboot-system")
                .register(meterRegistry);

        // 缓存命中率（Gauge 百分比）
        cacheHitRateGauge = Gauge.builder("cache_hit_rate_percent", this, this::calculateCacheHitRate)
                .description("缓存命中率")
                .tag("application", "iboot-system")
                .baseUnit(BaseUnits.PERCENT)
                .register(meterRegistry);
    }

    // 记录登录成功
    public void recordUserLoginSuccess() {
        userLoginSuccessCounter.increment();
        onlineUserCount.incrementAndGet();
    }

    // 记录登录失败
    public void recordUserLoginFailed() {
        userLoginFailedCounter.increment();
    }

    // 记录缓存命中
    public void recordCacheHit() {
        cacheHitCount.incrementAndGet();
        cacheTotalCount.incrementAndGet();
    }

    // 记录缓存未命中
    public void recordCacheMiss() {
        cacheTotalCount.incrementAndGet();
    }

    private double calculateCacheHitRate() {
        int total = cacheTotalCount.get();
        if (total == 0) return 0.0;
        return (double) cacheHitCount.get() / total * 100;
    }
}
```

**使用示例：**

```java
@Service
public class AuthService {

    @Autowired
    private BusinessMetricsService metricsService;

    public LoginResult login(String username, String password) {
        try {
            // 认证逻辑
            User user = authenticate(username, password);

            // 记录登录成功
            metricsService.recordUserLoginSuccess();

            return LoginResult.success(user);

        } catch (AuthenticationException e) {
            // 记录登录失败
            metricsService.recordUserLoginFailed();
            throw e;
        }
    }

    public <T> T executeBusinessProcess(String processType, Supplier<T> process) {
        // 开始计时
        Timer.Sample sample = metricsService.startBusinessProcess();

        try {
            T result = process.get();

            // 记录成功
            metricsService.recordBusinessProcessSuccess(sample, processType);

            return result;

        } catch (Exception e) {
            // 记录失败
            metricsService.recordBusinessProcessFailed(sample, processType);
            throw e;
        }
    }
}
```

### 11.7.2 Sentinel 治理指标

`iboot-sentinel` 通过 Sentinel 的 `MetricExtension` 扩展点把治理指标写入 Micrometer，所有指标统一带 `application` 标签（值为 `spring.application.name`），资源类指标额外带 `resource` 标签：

| 指标 | 类型 | 说明 |
|------|------|------|
| `sentinel_pass_total` | Counter | 通过量，按 `resource` |
| `sentinel_success_total` | Counter | 成功量，按 `resource` |
| `sentinel_block_total` | Counter | 阻塞量，按 `resource` 与 `rule`（flow/degrade/system/authority/param） |
| `sentinel_exception_total` | Counter | 业务异常量，按 `resource` |
| `sentinel_rt_seconds` | Timer | 响应时间，按 `resource`，可计算 p95 |
| `sentinel_threads` | Gauge | 资源当前并发线程数，按 `resource` |

常用 PromQL：

```promql
# 按资源查看限流阻塞速率
sum by (resource) (rate(sentinel_block_total{rule="flow"}[1m]))

# 按服务聚合熔断/降级阻塞
sum by (application) (rate(sentinel_block_total{rule="degrade"}[5m]))

# 按资源查看 RT p95
histogram_quantile(0.95, sum by (le, resource) (rate(sentinel_rt_seconds_bucket[5m])))
```

职责边界：**Sentinel Dashboard 只看单资源实时曲线与规则状态**，不承担长期存储与告警；**Prometheus/Grafana 负责跨实例聚合、告警与与 HTTP/JVM 指标同屏**。停 Dashboard 不影响 `sentinel_*` 指标的采集。

### 11.10 HTTP 请求监控过滤器

**MonitorFilter 实现：**

```java
@Component
@Order(1)
public class MonitorFilter implements Filter {

    @Autowired
    private MonitorUtils monitorUtils;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        String method = httpRequest.getMethod();
        String uri = httpRequest.getRequestURI();

        long startTime = System.currentTimeMillis();

        try {
            chain.doFilter(request, response);
        } finally {
            long duration = System.currentTimeMillis() - startTime;
            String outcome = String.valueOf(httpResponse.getStatus()).startsWith("2") ? "SUCCESS" : "FAILURE";

            // 记录请求计数和耗时
            monitorUtils.incrementRequest(uri, method, outcome);

            Timer.Sample sample = Timer.start(monitorUtils.getMeterRegistry());
            sample.stop(Timer.builder("http.server.requests")
                    .tag("method", method)
                    .tag("uri", uri)
                    .tag("status", String.valueOf(httpResponse.getStatus()))
                    .tag("outcome", outcome)
                    .register(monitorUtils.getMeterRegistry()));
        }
    }
}
```

### 11.11 Logback 配置

**logback-spring.xml：**

> 该文件位于 `iboot-kernel/src/main/resources/logback-spring.xml`，由九个依赖内核的业务服务共享；
> 网关与运维控制台不依赖内核，各自维护一份等价配置。
> appender 本身来自 `iboot-logging` 模块，三处配置都引用同一个类。
> 应用名通过 `<springProperty>` 取自 `spring.application.name`，新增服务无需修改日志配置。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <springProperty scope="context" name="APP_NAME" source="spring.application.name" defaultValue="iboot"/>
    <springProperty scope="context" name="LOG_HOME" source="iboot.logging.dir" defaultValue="logs"/>
    <springProperty scope="context" name="KAFKA_LOGGING_ENABLED" source="iboot.logging.kafka.enabled" defaultValue="false"/>
    <springProperty scope="context" name="KAFKA_BOOTSTRAP_SERVERS" source="iboot.logging.kafka.bootstrap-servers" defaultValue="localhost:29092"/>

    <!-- 控制台输出 -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{50} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <!-- 文件输出（滚动策略：按天 + 按大小） -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_HOME}/${APP_NAME}.log</file>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{50} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>${LOG_HOME}/${APP_NAME}-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <timeBasedFileNamingAndTriggeringPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP">
                <maxFileSize>100MB</maxFileSize>
            </timeBasedFileNamingAndTriggeringPolicy>
            <maxHistory>30</maxHistory>
        </rollingPolicy>
    </appender>

    <!-- 错误日志独立文件 -->
    <appender name="ERROR" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_HOME}/${APP_NAME}-error.log</file>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{50} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
        <filter class="ch.qos.logback.classic.filter.LevelFilter">
            <level>ERROR</level>
            <onMatch>ACCEPT</onMatch>
            <onMismatch>DENY</onMismatch>
        </filter>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>${LOG_HOME}/${APP_NAME}-error-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <maxFileSize>100MB</maxFileSize>
            <maxHistory>30</maxHistory>
        </rollingPolicy>
    </appender>

    <!-- Kafka 结构化投递：缓冲耗尽时丢弃，不阻塞业务线程 -->
    <appender name="KAFKA" class="com.iboot.logging.KafkaAppender">
        <enabled>${KAFKA_LOGGING_ENABLED}</enabled>
        <bootstrapServers>${KAFKA_BOOTSTRAP_SERVERS}</bootstrapServers>
        <topic>iboot-logs</topic>
        <clientId>${APP_NAME}</clientId>
        <ringBufferSize>8192</ringBufferSize>
        <encoder class="net.logstash.logback.encoder.LogstashEncoder">
            <customFields>{"app":"${APP_NAME}"}</customFields>
            <timestampPattern>yyyy-MM-dd'T'HH:mm:ss.SSS</timestampPattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
        <appender-ref ref="ERROR"/>
        <appender-ref ref="KAFKA"/>
    </root>

    <!-- 各服务的业务包级别由 application.yml 的 logging.level 配置 -->

</configuration>
```

### 11.11.1 日志投递开关

集中日志投递由两个属性控制，都通过 `<springProperty>` 读取：

| 属性 | 环境变量 | 默认值 | 说明 |
|---|---|---|---|
| `iboot.logging.kafka.enabled` | `IBOOT_LOGGING_KAFKA_ENABLED` | `false` | 是否创建 Kafka 生产者并投递 |
| `iboot.logging.kafka.bootstrap-servers` | `IBOOT_LOGGING_KAFKA_BOOTSTRAP_SERVERS` | `localhost:29092` | 宿主机默认指向映射端口 |

配置优先级：显式配置（`-D` 或环境变量）> 默认值。默认值的存在正是为了让「不配置」与「关闭」等价，且不产生任何连接。

| 场景 | 配置方式 | 预期行为 |
|---|---|---|
| 全栈 compose | `x-app-env` 内置 `true` 与 `kafka:9092`，无需手工设置 | 日志进 Kafka → Logstash → ES |
| `dev-init.sh`（宿主机跑 jar） | 不设置，落默认 `false` | 只输出控制台与本地文件，不创建生产者、不产生重连噪声 |
| `dev-init.sh` + 需要集中日志 | 先 `docker compose -f docker/docker-compose.yml up -d kafka kafka-init`，再带 `IBOOT_LOGGING_KAFKA_ENABLED=true IBOOT_LOGGING_KAFKA_BOOTSTRAP_SERVERS=localhost:29092` 启动 | 与 compose 一致 |
| 单元 / 集成测试 | 不设置，落默认 `false` | 测试不连接 Kafka，耗时不受影响；需要真实验证的用例显式开启 |

关闭状态下的行为：appender 仍会启动（仅用于生命周期一致），但 `append()` 直接返回，不创建生产者、不投递、不发起任何网络连接。

投递语义与排障：

- **至少一次**：发送超时后重试可能产生重复文档，ES 无唯一键；按「允许重复、不允许阻塞」处理。
- **丢弃告警**：环形缓冲耗尽时事件被丢弃，基类会按频率节流地写入 Logback status；停机时残留事件另有一条告警。排障时把 Logback status 打印出来即可看到。
- **间接信号**：Kibana 中按 `app` 过滤的日志量骤降，或 `kafka-consumer-groups.sh --describe` 显示的消费积压。

### 11.13 Logstash 配置

Logstash 不再监听任何 TCP 端口：服务侧只经 Kafka 投递，旧的 `5000`（TCP JSON）与 `5044`（Beats）入口都已移除。

**logstash.conf：**

```conf
input {
  # Kafka 缓冲层：服务经 Logback 投递到 iboot-logs，再由 Logstash 消费写入 ES。
  kafka {
    bootstrap_servers => "kafka:9092"
    topics => ["iboot-logs"]
    group_id => "iboot-logstash"
    codec => json
    auto_offset_reset => "latest"
    consumer_threads => 2
  }
}

filter {
  # 确保时间戳字段存在
  if [timestamp] {
    date {
      match => ["timestamp", "ISO8601"]
      target => "@timestamp"
      remove_field => ["timestamp"]
    }
  }

  # 移除不需要的字段
  mutate {
    remove_field => ["@version", "host", "port"]
  }
}

output {
  elasticsearch {
    hosts => ["http://elasticsearch:9200"]
    index => "iboot-logs-%{+YYYY.MM.dd}"
  }
}
```

`iboot-logs` topic 由 `kafka-init` 一次性创建（6 分区、副本 1、`retention.ms=86400000`），重复执行幂等。

**验证链路是否通：** 向 topic 灌入一条探针日志，再在 ES 中按 `app` 与 `traceId` 检索。

```bash

      --bootstrap-server localhost:9092 --topic iboot-logs

curl -s 'http://localhost:9200/iboot-logs-*/_search?q=app:iboot-probe%20AND%20traceId:probe-trace-1&pretty'
```

## 分布式追踪（Tracing）

链路追踪记录一次请求跨服务、跨中间件的完整路径。应用侧用 Boot 4 托管的 `spring-boot-starter-opentelemetry` 产生 span，经 OTLP/HTTP 上报到 Grafana Tempo；Grafana 以 Tempo 为数据源查询调用链，并通过 `traceId` 与 ELK 日志关联。

**组件与数据流：**

1. **应用侧**：各服务引入 `spring-boot-starter-opentelemetry`，`management.opentelemetry.tracing.export.otlp.endpoint` 指向 Tempo（容器内 `http://tempo:4318/v1/traces`，宿主机默认 `http://localhost:4318/v1/traces`）。
2. **传输与存储**：Tempo 在 4318 端口接收 OTLP/HTTP（4317 为 gRPC），trace 落本地磁盘，配置见 `docker/tempo/tempo.yaml`。
3. **查询**：Grafana 数据源 `Tempo` 指向 `http://tempo:3200`，服务图关联 Prometheus 数据源。
4. **关联**：日志中的 `traceId` 与 Tempo 的 trace 对应，可在 Kibana 中按 `traceId` 检索同一请求的日志上下文。

**开关与采样：**

- `IBOOT_TRACING_ENABLED`（默认 `true`）控制是否产生 span。
- `IBOOT_TRACING_SAMPLE`（默认 `1.0`）为采样概率；压测或生产按需调低。
- `TEMPO_OTLP` 覆盖 OTLP 上报地址。

> 指标仍走 Prometheus（`management.otlp.metrics.export.enabled=false`），避免与既有看板重复采集。

### 11.14 Prometheus 告警规则

**alerts/iboot-alerts.yml：**

```yaml
groups:
  - name: iboot-application
    interval: 30s
    rules:
      # 应用宕机告警
      - alert: ApplicationDown
        expr: up{application="iboot-system"} == 0

          severity: critical

        expr: |
          sum(rate(http_server_requests_seconds_count{outcome="SERVER_ERROR"}[5m]))
          / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "HTTP 错误率过高"

      - alert: DbConnectionPoolExhausted

        annotations:

        for: 10m

          severity: warning

      # 登录失败率告警
      - alert: HighLoginFailedRate
        expr: |
          rate(user_login_failed_total[5m]) / rate(user_login_success_total[5m]) > 0.5
```

### 11.22 数据保留策略

| 分辨率 | 保留时间 | 说明 |

| 原始数据（Raw） | 30 天 | 15s 采样间隔的原始指标数据 |
| 5 分钟聚合 | 90 天 | 每 5 分钟聚合一次，存储空间减少约 20 倍 |
| 1 小时聚合 | 1 年 | 每小时聚合一次，存储空间减少约 240 倍 |

## 监控指标详解

### 11.23 指标类型说明

| 类型 | 描述 | 使用场景 | 示例 |
|------|------|----------|------|
| Counter | 只增计数器，重启归零 | 请求次数、错误次数 | `user_login_success_total` |
| Gauge | 可增可减的瞬时值 | 内存使用、在线用户数 | `user_online_count` |
| Histogram | 直方图，支持分位数计算 | 请求延迟、响应大小 | `http_server_requests_seconds` |
| Summary | 服务端计算分位数 | 对分位数精度要求高的场景 | - |
| Timer | Micrometer 封装，基于 Histogram | 方法耗时统计 | `@Timed` 注解 |

### 11.24 核心业务指标清单

| 指标名称 | 类型 | 描述 | 标签 |
|----------|------|------|------|
| `user_login_success_total` | Counter | 用户登录成功次数 | application, namespace |
| `user_login_failed_total` | Counter | 用户登录失败次数 | application, namespace |
| `user_online_count` | Gauge | 当前在线用户数量 | application, namespace |
| `business_process_duration_seconds` | Histogram | 业务流程处理耗时 | application, process_type, result |
| `business_process_success_total` | Counter | 业务流程成功次数 | application |
| `business_process_failed_total` | Counter | 业务流程失败次数 | application |
| `cache_hit_rate_percent` | Gauge | 缓存命中率（%） | application |

**SSE 推送指标说明：**

- `push_connection_active`：实时反映当前建立 SSE 连接的用户数量，可用于评估系统负载

- `push_event_failed_total`：累计推送失败的事件数量，结合成功次数可计算推送成功率

```promql
# 推送成功率（5 分钟滑动窗口）
```


**后端指标注册代码：**
```java
@Component
public class BusinessMetricsService {

    private AtomicInteger pushConnectionCount;
    private Counter pushEventSentCounter;
    private Counter pushEventFailedCounter;

    @PostConstruct
    public void init() {
        // 推送连接数（Gauge）
        pushConnectionCount = new AtomicInteger(0);
        Gauge.builder("push_connection_active", pushConnectionCount, AtomicInteger::get)
                .description("当前活跃的 SSE 推送连接数")
                .tag("application", "iboot-system")
                .register(meterRegistry);

        // 推送成功次数（Counter）
        pushEventSentCounter = Counter.builder("push_event_sent_total")
                .description("推送事件发送成功次数")
                .tag("application", "iboot-system")
                .register(meterRegistry);

        // 推送失败次数（Counter）
        pushEventFailedCounter = Counter.builder("push_event_failed_total")
                .description("推送事件发送失败次数")
                .tag("application", "iboot-system")
                .register(meterRegistry);
    }

    public void updatePushConnectionCount(int count) {
        pushConnectionCount.set(count);
    }

    public void recordPushEventSent() {
        pushEventSentCounter.increment();
    }

    public void recordPushEventFailed() {
        pushEventFailedCounter.increment();
    }
}
```

**查询特定接口的错误日志：**
```
uri: "/api/users/*" AND level: ERROR
```

### 11.31 故障排查流程

```
1. 收到告警通知
   │
   ▼
2. 查看 Grafana 仪表板，确认告警指标趋势
   │
   ▼
3. 根据告警类型定位问题：
   ├─ 应用宕机 → 检查应用日志、JVM 状态
   ├─ HTTP 错误率高 → 查看错误日志、异常堆栈
   ├─ 延迟过高 → 分析慢查询、GC 日志
   └─ 资源不足 → 检查 CPU、内存、磁盘使用率
   │
   ▼
4. Kibana 搜索相关日志
   │
   ▼
5. 根据日志和指标分析根因
   │
   ▼
6. 采取措施修复问题
   │
   ▼
7. 验证修复效果，关闭告警
```

### 11.32 性能优化建议

**Prometheus 优化：**

| 优化项 | 建议值 | 说明 |
|--------|--------|------|
| 采集间隔 | 15s | 平衡数据精度和存储成本 |
| 数据保留 | 24h 本地 + Thanos 长期存储 | 减少本地存储压力 |
| 抓取超时 | 10s | 避免慢目标影响整体采集 |
| 最大样本数 | 100000 | 防止内存溢出 |

**Elasticsearch 优化：**

| 优化项 | 建议值 | 说明 |
|--------|--------|------|
| JVM 堆内存 | 512MB-1GB | 日志量适中场景 |
| 分片数 | 1-3 个/索引 | 根据数据量调整 |
| 副本数 | 0-1 | 单节点设为 0 |
| 索引保留 | 30 天 | 定期删除旧索引 |

**Grafana 优化：**

| 优化项 | 建议值 | 说明 |
|--------|--------|------|
| 查询超时 | 60s | 避免长查询阻塞 |
| 最大数据点 | 1000 | 限制图表渲染数据量 |
| 刷新间隔 | 30s | 平衡实时性和负载 |

### B. 监控指标命名规范

遵循 Micrometer 命名规范：

```
<领域>_<操作>_<单位>_<统计类型>

示例：
- user_login_success_total      # Counter 类型
- business_process_duration_seconds  # Timer/Histogram 类型
- cache_hit_rate_percent        # Gauge 类型
- file_upload_size_bytes        # DistributionSummary 类型
```

### C. 日志级别使用规范

| 级别 | 使用场景 |
|------|----------|
| ERROR | 系统错误，需要人工介入 |
| WARN | 异常情况，但系统仍可继续运行 |
| INFO | 重要业务流程节点 |
| DEBUG | 开发调试信息 |
| TRACE | 详细追踪信息（生产环境禁用） |
