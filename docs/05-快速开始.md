## 后端启动

### 5.4 克隆项目

```bash
git clone <repository-url>
cd iboot
```

后续命令默认在仓库根目录执行；多服务启动统一由 `scripts/dev-init.sh` 负责。

### 5.5 准备配置与密钥

复制配置模板并填写本机密钥：

```bash
cp .env.example .env
```

至少需要填写：

| 变量 | 用途 |
|---|---|
| `DASHSCOPE_CHAT_API_KEY` / `DASHSCOPE_EMBEDDING_API_KEY` | AI 工作台对话与向量化；缺失时 `iboot-ai` 拒绝启动 |
| `MYSQL_ROOT_PASSWORD` | 仅在 MySQL 容器内回环首次引导使用；不再从编排网络或宿主机登录 |
| `MYSQL_MIGRATOR_PASSWORD` / `MYSQL_PROVISIONER_PASSWORD` | `iboot-db-init` 的迁移口令与账号初始化口令；均不注入业务服务 |
| `MIDDLEWARE_<SERVICE>_PASSWORD` | 每个服务各自的 MySQL/Redis/Nacos 口令，十个服务各一份 |
| `SILO_ROOT_PASSWORD` / `SILO_*_SECRET_KEY` | Silo 根账号与服务桶账号 |
| `JWT_SECRET` | 可选；生产必须覆盖默认开发值 |

完整变量表见 [08-部署指南 §8.6](./08-部署指南.md) 与根目录 `.env.example`。`.env` 已在
`.gitignore` 中，不要提交。

### 5.6 数据库与 TLS 初始化

数据库 `iboot`、全部表结构、每服务 MySQL 账号与表级授权、Redis ACL 都由初始化脚本完成，
**不需要手工建库，也不需要修改 `application-dev.yml`**：

- `scripts/dev-init.sh` 调用 `iboot-db-init` 建库建表，随后执行 `mysql-users-init` 与
  `mysql-grants-init` 创建账号并收紧到表级权限。
- 首次启动会自动调用 `scripts/tls-init.sh` 生成本地 CA、服务证书与 Java 信任库；
  浏览器信任需另外执行一次 `CAROOT=docker/certs/ca mkcert -install`。
- 业务服务不再自带 Flyway（`spring.flyway.enabled=false`），也不接受明文数据库连接：
  JDBC 默认 `MYSQL_SSL_PARAMS=sslMode=VERIFY_IDENTITY&requireSSL=true&...`。

生产环境同样只通过环境变量注入连接参数，不在仓库内保存口令：

```yaml
spring:
  datasource:
    druid:
      url: jdbc:mysql://${MYSQL_HOST}:${MYSQL_PORT:3306}/iboot?${MYSQL_SSL_PARAMS:sslMode=VERIFY_IDENTITY&requireSSL=true}
      username: ${MYSQL_USERNAME}
      password: ${MYSQL_PASSWORD}
  data:
    redis:
      host: ${REDIS_HOST}
      username: ${REDIS_USERNAME}
      password: ${REDIS_PASSWORD}
      ssl:
        enabled: true
```

### 5.7 数据库迁移

数据库的建库与全部迁移由 `iboot-db-init` 统一执行，服务进程不再执行迁移。

**迁移脚本位置：**

```
iboot-db-init/src/main/resources/db/migration/
├── V1__baseline.sql            # 单库结构与种子数据
└── V2__... ~ V*.sql            # 增量迁移
```

**手动执行（使用 `.env` 中的迁移账号口令与 TLS 信任库）：**

```bash
set -a; source .env; set +a
mvn -pl iboot-db-init -am package
MYSQL_HOST=localhost MYSQL_PORT=3306 MYSQL_USERNAME=iboot_migrator \
  MYSQL_PASSWORD="$MYSQL_MIGRATOR_PASSWORD" MYSQL_TLS_ENABLED=true \
  java -Djavax.net.ssl.trustStore=docker/certs/truststore.p12 \
       -Djavax.net.ssl.trustStorePassword=changeit \
       -jar iboot-db-init/target/iboot-db-init-1.0.0-exec.jar
```

### 5.8 启动后端

**推荐：一键启动**
```bash
scripts/dev-init.sh
```

脚本会启动中间件、集中日志链路（Kafka/Logstash）、可观测平台（Prometheus/Grafana/Kibana/
Alertmanager/Thanos）与 Sentinel Dashboard，写入基线规则、按需构建、执行 `iboot-db-init`、
按顺序启动九个业务服务与运维控制台，并等待健康。默认启用 TLS：脚本会调用
`scripts/tls-init.sh` 生成本地 CA 与证书；浏览器信任需另外执行一次
`CAROOT=docker/certs/ca mkcert -install`。B2 起服务端口与门户→网关、服务间、
JWKS、MySQL/Redis/Silo 也使用 TLS；B3 起 ES/Kafka/Logstash 也只走 TLS；B4 起 Nacos 的 HTTP 与 gRPC 也只接受 TLS。
内部 TLS 的排障与回退见 [docs/27](<./27-TLS 与零信任操作指南.md>)。登录门户后可通过“微服务治理”菜单打开
Nacos 与 Sentinel 控制台；开发环境内嵌，生产环境只跳转。
内网或镜像环境可在 `mvn` 后追加 `-s <settings.xml>`；`dev-init.sh` 会优先使用
`$MAVEN_SETTINGS`，未设置时自动使用 `$HOME/repo/settings.xml`（若存在）。

集中日志默认开启，运行日志页面依赖该链路；资源紧张时可在 `.env` 设
`IBOOT_LOGGING_KAFKA_ENABLED=false` 关闭投递，或设 `IBOOT_OBSERVABILITY_ENABLED=false`
跳过可观测平台。手工启用细节见 [docs/11 §11.11.1](./11-可观测性设计.md)。

**只启动单个服务（调试）**
```bash
set -a; source .env; set +a
mvn -pl iboot-system spring-boot:run \
  -Dspring-boot.run.jvmArguments="-Djavax.net.ssl.trustStore=docker/certs/truststore.p12 -Djavax.net.ssl.trustStorePassword=changeit"
```

**运行 JAR 包**
```bash
mvn -pl iboot-system -am package -DskipTests
java -jar iboot-system/target/iboot-system-1.0.0.jar
```

**使用 IDEA 启动**
主类为 `com.iboot.system.IBootSystemApplication`；多服务联调仍建议使用 `dev-init.sh`，避免只启动系统服务时其它服务不可达。

### 5.8.1 启动 AI 服务

AI 工作台是独立服务（8081），需要 Redis、MySQL（共享库 `iboot`）、Elasticsearch、Silo 与 `iboot-system` 已启动。

1. 在根目录 `.env` 中配置百炼与知识库变量：

```ini
DASHSCOPE_CHAT_API_KEY=sk-...
DASHSCOPE_EMBEDDING_API_KEY=sk-...
DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode

MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_USERNAME=iboot_ai
MYSQL_PASSWORD=<与 MIDDLEWARE_AI_PASSWORD 相同>
IBOOT_AI_MYSQL_DATABASE=iboot
ELASTICSEARCH_URIS=https://localhost:9200
ELASTICSEARCH_USERNAME=elastic
ELASTICSEARCH_PASSWORD=iboot-dev-elastic
ELASTIC_PASSWORD=iboot-dev-elastic
IBOOT_AI_SILO_ENDPOINT=https://localhost:9000
IBOOT_AI_SILO_ACCESS_KEY=iboot_ai
IBOOT_AI_SILO_SECRET_KEY=<与 SILO_AI_SECRET_KEY 相同>
IBOOT_AI_SILO_BUCKET=iboot-ai
IBOOT_AI_RAG_ENABLED=true
```

2. 创建 Silo `iboot-ai` bucket（命令见 [22-AI 工作台操作指南](./22-AI 工作台操作指南.md)）。

3. 启动服务：

```bash
set -a; source .env; set +a
mvn -pl iboot-ai spring-boot:run
```

4. 验证：

```bash
curl --cacert docker/certs/ca/rootCA.pem \
     --cert docker/certs/services/ai.pem --key docker/certs/services/ai-key.pem \
     https://localhost:8081/actuator/health
```

登录前端后进入「AI 工作台 → 智能对话」或「知识库」。iboot-system 执行 `V25` 菜单迁移后需重新登录。完整配置与排障见 [22-AI 工作台操作指南](./22-AI 工作台操作指南.md)。

知识图谱（1.4）为可选能力，默认关闭：先 `docker compose --profile graph up -d neo4j`，再把 `IBOOT_AI_GRAPH_ENABLED` 置为 `true` 启动 `iboot-ai`，然后以超管登录态调用 `POST /api/ai/graph/sync` 完成入图，详见 [22-AI 工作台操作指南](./22-AI 工作台操作指南.md) §13。

### 5.11 后端启动验证

**验证步骤：**

1. **检查进程是否运行**
   ```bash
   jps -l | grep iboot
   # 应显示类似：12345 com.iboot.system.IBootSystemApplication
   ```

2. **检查端口监听**
   ```bash
   netstat -tlnp | grep 8080
   # 应显示：tcp  0  0 0.0.0.0:8080  0.0.0.0:*  LISTEN  12345/java
   ```

3. **检查日志文件**
   ```bash
   tail -f logs/iboot-system.log
   # 应看到应用启动成功的日志
   ```

4. **测试认证端点**
   ```bash
   # OIDC 发现文档：经门户 HTTPS 入口访问认证服务
   curl -sS --cacert docker/certs/ca/rootCA.pem \
     https://localhost:5173/.well-known/openid-configuration \
     | jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri}'
   ```
   浏览器登录走授权码 + PKCE：未登录访问门户时会被跳转到认证服务的登录页
   （`https://localhost:5173/login`），登录成功后回到原先要访问的页面。旧的用户名密码
   登录接口已下线，不再作为客户端入口。

5. **检查服务治理组件**
   - Sentinel Dashboard：<https://localhost:8858>（HTTPS + 登录，默认 `sentinel` / `sentinel123`）；
   - Nacos 控制台：<https://localhost:8849/next/>（本地开发默认关闭控制台登录）；
   - 门户入口：登录后访问“微服务治理”下的 Nacos / Sentinel 控制台；
   - 基线规则：`bash scripts/sentinel-init.sh --verify`；
   - 规则与演练说明见 [23-微服务底座操作指南 §13](./23-微服务底座操作指南.md)。

### 5.12 配置文件

**开发环境配置（.env）：**

修改 `iboot-portal/.env` 文件：

```bash
# 应用标题
VITE_APP_TITLE=iBoot 管理系统

# API 基础路径
VITE_API_BASE_URL=/iboot/api

# 是否启用 sourcemap
VITE_SOURCE_MAP=true

# 版本号
VITE_APP_VERSION=1.0.0

# OAuth2 / OIDC 公开来源；宿主机开发以 Vite 为唯一入口
VITE_OIDC_ISSUER=https://localhost:5173
```

**代理与 HTTPS（vite.config.ts）：**

完整配置以 `iboot-portal/vite.config.ts` 为准。证书由 `scripts/tls-init.sh` 生成，要点：

- 开发服务器以 HTTPS 启动，使用 `docker/certs/portal.pem` 与 `portal-key.pem`。
- `/api`、`/iboot/api`、`/oauth2`、`/.well-known`、`/login` 与运维控制台都反代到
  `https://localhost:8088` / `https://localhost:8089`，并出示门户客户端证书
  （`ca` / `cert` / `key`），否则服务端 mTLS 会拒绝连接。
- OIDC 必须保留原始 Host，认证服务据此生成公开地址；`/iboot/api` 重写为 `/api`。
- 设置 `IBOOT_INTERNAL_TLS_ENABLED=false` 可临时回退到 HTTP 上游，仅用于排障。

## Docker 部署

全栈容器化由 `scripts/docker-deploy.sh` 与 `docker/docker-compose.yml` 负责；镜像构建、服务清单、端口与排障的权威说明见 [`docker/README.md`](../docker/README.md)。

### 5.20 启动所有服务

```bash
# 核心 + 可观测性（默认）
scripts/docker-deploy.sh up

# 只启动核心组件
scripts/docker-deploy.sh up core
```

该命令会构建后端与前端镜像、启动 Compose，并轮询服务健康状态。

### 5.20.1 对象存储默认配置

全量 Docker 部署默认使用 Silo 对象存储：

| 项目 | 容器内 | 宿主机开发 |
|------|--------|------------|
| 存储类型 | `silo`（Compose 固定） | `silo`（迁移后的 `sys_config` 默认值） |
| 内网端点 | `https://silo:9000` | `https://localhost:9000` |
| 预签名端点 | `https://localhost:9000` | `https://localhost:9000` |

- 容器内的 endpoint 由 `docker-compose.yml` 的 `x-app-env` 注入，不会继承 `.env` 中的 `localhost` 值；
- 宿主机开发如需本地磁盘，在 `.env` 设置 `IBOOT_FILE_STORAGE_TYPE=local`，Docker 仍固定为 `silo`；
- 切换存储类型后需重启 `iboot-file`、`iboot-system`、`iboot-job`，因为策略在启动期选定；
- 切换不会迁移既有本地文件，旧文件需要先导出，或把存储类型改回 `local` 再重启；
- 生产环境通过 `IBOOT_FILE_SILO_ENDPOINT`、`IBOOT_FILE_SILO_PUBLIC_ENDPOINT` 与凭据环境变量注入，
  公网预签名地址必须使用 HTTPS。

### 5.20.2 Tempo 链路追踪入口

门户“可观测平台 → Tempo 链路追踪”（权限码 `monitor:tempo`）以 kiosk 模式嵌入 Grafana Explore，
数据源固定为 `tempo`。使用前需要 Grafana（3000）与 Tempo（3200，HTTPS）已启动；Grafana 地址读取
`sys_config` 的 `sys.grafana.monitor.url`。Tempo 自身没有独立查询界面，链路搜索、TraceQL 与
服务图都在 Grafana Explore 中完成。

## 常见问题

### 5.27 后端启动失败

**问题 1：端口被占用**
```
Port 8080 was already in use.
```

**解决方案：**
```bash
# 查找占用端口的进程
lsof -i :8080
# 杀死进程
kill -9 <PID>

# 或修改配置更换端口
server:
  port: 8081
```

**问题 2：数据库连接失败**
```
com.mysql.cj.jdbc.exceptions.CommunicationsException: Communications link failure
```

**解决方案：**
1. 检查 MySQL 是否启动：`docker ps | grep mysql` 或 `systemctl status mysqld`
2. 检查数据库连接配置是否正确
3. 检查防火墙设置

**问题 3：Redis 连接失败**
```
io.lettuce.core.RedisConnectionException: Unable to connect to localhost:6379
```

**解决方案：**
1. 检查 Redis 是否启动：`docker ps | grep redis` 或 `systemctl status redis`
2. 检查 Redis 配置：`redis-cli ping` 应返回 `PONG`

### 5.28 前端启动失败

**问题 1：依赖安装失败**
```
npm ERR! code ERESOLVE
```

**解决方案：**
```bash
# 清理缓存
cnpm cache clean --force
# 删除 node_modules
rm -rf node_modules package-lock.json
# 重新安装
cnpm install
```

**问题 2：开发服务器启动失败**
```
Error: listen EADDRINUSE: address already in use 0.0.0.0:5173
```

**解决方案：**
```bash
# 查找占用端口的进程
lsof -i :5173
# 杀死进程
kill -9 <PID>

# 或修改 vite.config.ts 更换端口
server: {
  port: 3001
}
```

**问题 3：代理请求失败**
```
Error: connect ECONNREFUSED 127.0.0.1:8080
```

**解决方案：**
1. 确认后端服务已启动
2. 检查代理配置 `vite.config.ts` 中的 `target` 地址
3. 检查后端服务监听的地址和端口

### 5.29 Docker 相关问题

**问题 1：容器启动失败**
```
Error starting userland proxy: listen tcp4 0.0.0.0:3306: bind: address already in use
```

**解决方案：**
```bash
# 停止本地 MySQL 服务
sudo systemctl stop mysqld

# 或修改 docker-compose.yml 更换端口
ports:
  - "3307:3306"
```

**问题 2：容器间网络不通**
```
Unable to connect to mysql:3306
```

**解决方案：**
1. 确保所有服务在同一个 Compose 网络中
2. 使用服务名而非 localhost 访问（如 `mysql` 而非 `127.0.0.1`）
3. 检查网络配置：`docker network ls`

### 5.30 登录问题

**问题：无法登录**
```
登录失败：用户名或密码错误
```

**解决方案：**
1. 确认数据库已正确初始化
2. 检查默认账号是否存在：
   ```sql
   SELECT * FROM sys_user WHERE username = 'admin';
   ```
3. 检查密码加密是否正确（BCrypt）
4. 查看后端日志定位具体错误

**问题：登录后提示无权限**
```
403 Forbidden
```

**解决方案：**
1. 检查用户是否分配了角色
2. 检查角色是否分配了菜单权限
3. 清除浏览器缓存后重新登录
