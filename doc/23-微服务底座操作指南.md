# 23 - 微服务底座操作指南

> 适用变更：`openspec/changes/add-microservice-foundation`
>
> 本文只覆盖**回归基线与网关**相关的操作。Nacos、链路追踪等章节在对应任务交付时补充。

## 1. 回归基线是什么

阶段 2 要把单体拆成多个服务。拆分最容易造成的三类损伤是：**接口路径漂移**、**权限判定变化**、**关键链路中断**。这三类问题都不会让编译失败，只会让用户在使用时撞见，因此需要一套能在拆分前后反复执行的检查。

`scripts/regress/` 提供四项检查：

| 脚本 | 检查内容 | 依赖 |
|---|---|---|
| `api-snapshot.sh` | 导出服务的 OpenAPI 并归一化为基线 | 服务已启动 |
| `route-coverage.sh` | 每条接口路径都能被唯一路由规则解析 | `golden/` 与 `routes.txt` |
| `smoke.sh` | 六条关键链路端到端可用 | 全栈（中间件 + 8080/8081） |
| `permission-matrix.sh` | 角色 × 接口 × 期望结果 | 全栈 |

`regress.sh` 是唯一入口，按「快照 → 路由覆盖 → 冒烟 → 权限矩阵」顺序执行，任一失败即非零退出。

## 2. 前置条件

1. 中间件与两个后端服务已启动：

   ```bash
   cd docker && docker compose up -d mysql redis minio minio-init elasticsearch
   ```

2. `iboot-admin` 需开启备份能力，否则冒烟的备份链路会失败：

   ```bash
   IBOOT_BACKUP_ENABLED=true java -jar iboot-admin/target/iboot-admin-1.0.0.jar
   ```

3. `iboot-ai` 需要 `iboot_ai` schema（首次使用全新 MySQL 数据卷时手动创建）：

   ```bash
   docker exec iboot-mysql mysql -uroot -proot \
     -e "CREATE DATABASE IF NOT EXISTS iboot_ai CHARACTER SET utf8mb4"
   ```

4. 默认账号 `admin / admin123456`，可用环境变量覆盖：

   | 变量 | 默认值 | 说明 |
   |---|---|---|
   | `REG_BASE` | `http://localhost:8080` | 管理端地址 |
   | `REG_AI_BASE` | `http://localhost:8081` | AI 服务地址 |
   | `REG_USER` | `admin` | 登录账号 |
   | `REG_PASS` | `admin123456` | 登录密码 |

## 3. 日常用法

```bash
# 与基线比对，有漂移即失败
bash scripts/regress/regress.sh

# 确认差异合理后，重新生成基线
bash scripts/regress/regress.sh --refresh
```

`--refresh` 会把当前导出结果写入 `scripts/regress/golden/`，并以它作为新的标准答案。**只在确认差异是预期的接口变更时使用**，否则等于把错误固化成基线。

## 4. 允许差异登记

接口发生变化时，按以下顺序处理：

1. 先判断差异是否属于本次变更的预期行为。路径、方法、必填参数、响应结构的变化一律视为**不允许**，除非本次变更明确就要改它。
2. 属于预期变化时，在变更说明中写清：改了哪条接口、为什么必须改、影响哪些调用方。
3. 执行 `--refresh` 刷新基线，并把新的 `golden/` 文件随代码一并提交。
4. 仅新增接口（不修改既有接口）时同样需要刷新基线，但在说明中单独列出新增项。

未登记的差异会让 `regress.sh` 失败，这是有意设计的——**沉默的漂移比显式的失败更贵**。

## 6. 已知约束

- **AI 服务的 `/v3/api-docs` 需要鉴权**，因此 `api-snapshot.sh` 会在设置了 `REG_TOKEN` 时附带令牌；`regress.sh` 会先登录再导出。
- **响应体被 CloudEvent 信封包裹**，分页接口还额外嵌套一层 `PageResult`（数据位于 `.data.data`），脚本中的 `jq` 表达式已按此编写。
- **数据权限依赖 SQL 别名**：`@DataScope` 上声明的别名必须与 mapper XML 中的表别名一致。新增带数据权限的查询时，若 XML 未起别名，会直接报 `Unknown column` 而不是静默失效——这是刻意保留的失败方式，便于立即发现。
- 权限矩阵会在库里创建并清理 `ROLE_SCOPE_TEST` / `regress_scope`；冒烟会保留一个 `regress_approver` 账号（审批人不能是本人，所以必须有第二个用户）。

## 7. 网关

### 7.1 端口与启动

| 项 | 值 |
|---|---|
| 端口 | `8088` |
| 启动 | `java -jar iboot-gateway/target/iboot-gateway-1.0.0.jar` |
| 健康检查 | `GET http://localhost:8088/actuator/health` |
| 路由查看 | `GET http://localhost:8088/actuator/gateway/routes`（仅 `local` 等已开启端点的 profile） |

### 7.2 Profile

| profile | 后端地址来源 | 用途 |
|---|---|---|
| `local`（默认） | `IBOOT_ADMIN_URI` / `IBOOT_AI_URI` 静态地址 | 本地开发，不依赖注册中心 |
| `nacos` | 服务名 + 服务发现 | 接入注册中心后使用 |

`local` profile 的价值在于：注册中心没起来时仍能调通业务代码；排查线上问题时也可以用静态地址绕过注册中心。

### 7.3 路由表

按「具体前缀优先」排列，兜底放最后：

| order | id | 路径 | 目标 |
|---|---|---|---|
| 0 | `notify-sse` | `/api/push/**` | 通知服务（长连接，`response-timeout: -1`） |
| 10 | `ai` | `/api/ai/**` | AI 服务 |
| 20 | `file` | `/api/file/**` | 文件服务 |
| 25 | `notify` | `/api/message/**`、`/api/notice/**`、`/api/notification/**`、`/api/search` | 通知服务 |
| 28 | `job` | `/api/monitor/backup/**`、`/api/job/**` | 调度服务（备份按路径级登记，见 §11.8） |
| 30 | `auth` | `/api/auth/login`、`/api/auth/logout`、`/api/auth/register`、`/oauth2/**`、`/.well-known/**`、`/connect/**`、`/login` | 认证服务 |
| 100 | `admin` | `/api/**` | 管理端（兜底） |

**每拆出一个服务，就在 admin 兜底之前插入一条更具体的前缀。** 路由表是拆分的开关，也是回滚点。

### 7.4 跨域

跨域统一由网关处理（`spring.cloud.gateway.server.webflux.globalcors`），预检请求由网关直接应答、不转发到后端。后端服务不再各自维护跨域配置。

### 7.5 长连接推送

`/api/push/**` 单独成一条路由，并设置 `response-timeout: -1`：

- 不套用全局 10 秒响应超时，否则长连接会被定时切断；
- 查询参数中的凭证（`?t=token`）原样透传，网关不改写。

### 7.6 故障响应

上游不可用或超时不再返回无信息的 500，而是可区分的 JSON：

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 上游连接被拒 | `503` | `{"code":503,"message":"上游服务不可用","path":"..."}` |
| 上游响应超时 | `504` | `{"code":504,"message":"上游服务响应超时","path":"..."}` |
| 其它未预期异常 | `500` | `{"code":500,"message":"网关内部错误","path":"..."}` |

单个服务故障只影响对应前缀：管理端不可用时 `/api/ai/**` 仍然正常。

### 7.7 回滚

网关本身的回滚有两个层级，都不需要改业务代码：

1. **改回直连**：把 portal 的 Vite 代理与 nginx 目标从 `8088` 改回 `8080` / `8081`。
2. **路由回退**：把某个已迁移前缀的路由目标改回管理端，admin 旧实现保留一个发布周期。

### 7.8 测试

`iboot-gateway` 自带 6 个集成测试，用本地桩服务覆盖：兜底转发、具体前缀优先、推送通道转发、跨域预检、上游不可用降级、单点故障隔离。

```bash
mvn -s /home/lam/repo/settings.xml -pl iboot-gateway test
```

## 8. 注册中心与配置中心

### 8.1 服务名与端口

| 服务 | 注册名 | 端口 |
|---|---|---|
| 管理端 | `iboot-admin` | 8080 |
| AI 服务 | `iboot-ai` | 8081 |
| 网关 | `iboot-gateway` | 8088 |

注册名与各服务的 `spring.application.name` 一致，日志与指标中的服务标识因此统一。

### 8.2 配置接入

Nacos 3.x **不再支持 `bootstrap.yml`**，配置一律通过 `spring.config.import` 引入：

```yaml
spring:
  config:
    import: optional:nacos:iboot-admin.yml
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:localhost:8848}
        enabled: ${IBOOT_NACOS_ENABLED:true}
        fail-fast: false
      config:
        server-addr: ${NACOS_ADDR:localhost:8848}
        file-extension: yml
        enabled: ${IBOOT_NACOS_ENABLED:true}
```

`optional:` 前缀保证配置中心不可用时仍能以本地配置启动。

### 8.3 注册中心故障时的行为

`spring.cloud.nacos.discovery.fail-fast` 默认值为 `true`，注册失败会让整个应用启动失败（实测 120 秒后崩溃）。本项目统一设为 `false`：

- 注册中心不可用时，管理端仍能在约 20 秒内启动并对外提供服务；
- 注册失败在日志中可见，不会静默；
- 注册中心恢复后，心跳任务会自动重新注册，无需人工重启。

### 8.4 网关的两种 profile

| profile | 转发方式 | 使用场景 |
|---|---|---|
| `local` | 静态地址 `http://localhost:8080` / `8081` | 注册中心未启动时开发 |
| `nacos` | `lb://iboot-admin` / `lb://iboot-ai` | 正常联调与验证 |

切换：`java -jar iboot-gateway-*.jar --spring.profiles.active=nacos`

### 8.5 验证热更新

管理端的 `/actuator/env` 默认对值脱敏（显示 `******`），不能直接用来观察配置值。推荐用**有外部可观测行为**的配置项验证，例如备份开关：

```bash
# 1. 记录进程启动时间
curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/actuator/metrics/process.start.time

# 2. 经 Nacos 下发 iboot.backup.enabled=true，备份接口应成功
curl -X POST http://localhost:8848/nacos/v1/cs/configs \
  --data-urlencode dataId=iboot-admin.yml --data-urlencode group=DEFAULT_GROUP \
  --data-urlencode "content=iboot:
  backup:
    enabled: true" --data-urlencode type=yaml

# 3. 再下发 false，备份接口应返回「备份功能未启用」
# 4. 两次启动时间相同，说明未重启
```

**注意**：环境变量优先级高于配置中心。若同时设置了 `IBOOT_BACKUP_ENABLED`，Nacos 里的值不会生效——验证热更新时不要设置同名环境变量。

### 8.6 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 容器起不来，日志提示 `NACOS_AUTH_TOKEN must be set` | Nacos 3.x 镜像即使关闭鉴权也要求令牌 | compose 已提供开发用令牌 |
| 控制台打不开 | Nacos 3.x 控制台与主端口分离 | 访问 `http://localhost:8849/`，不带 `/nacos` 前缀 |
| 服务启动失败，`ErrCode:-401 Client not connected` | `fail-fast` 为默认 true | 设为 `false` |

## 9. 链路追踪

### 9.1 依赖与配置

Boot 4 把追踪自动配置拆成了独立 starter：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-opentelemetry</artifactId>
</dependency>
```

只加 `micrometer-tracing-bridge-otel` 不够——应用能启动，但不会导出任何 span。

配置（以管理端为例）：

```yaml
management:
  tracing:
    export:
      enabled: ${IBOOT_TRACING_ENABLED:true}      # 总开关
    sampling:
      probability: ${IBOOT_TRACING_SAMPLE:1.0}    # 采样比例（默认全采）
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: ${TEMPO_OTLP:http://localhost:4318/v1/traces}
  otlp:
    metrics:
      export:
        enabled: false                            # 指标仍走 Prometheus
```

> 属性名在 Boot 4 变更：旧的 `management.otlp.tracing.endpoint` 不再识别，必须用
> `management.opentelemetry.tracing.export.otlp.endpoint`。
>
> 总开关同样是新名字：`management.tracing.enabled` 在 Boot 4 已不起作用（能启动、不报错，
> 但追踪照常导出），必须用 `management.tracing.export.enabled`。这个坑很难从现象上看出来——
> 设了旧属性后行为毫无变化。
>
> 采样默认值从 `0.1` 调到了 `1.0`：0.1 会让"链路是否贯通"的验证变成概率事件，十次里九次
> 查不到。压测或生产按需用 `IBOOT_TRACING_SAMPLE` 调低。

### 9.2 跨服务传播的前提

出站 HTTP 必须使用 Boot 自动配置的 `RestClient`：

- 需要 `spring-boot-starter-restclient`（Boot 4 同样拆成了独立 starter）；
- 不要手写 `RestClient.builder()`，它没有观测能力，下游会另起一条链路；
- 手工构建时至少要挂 `ObservationRegistry`，否则同样不传播。

### 9.3 日志关联

管理端的日志格式已包含 `[traceId,spanId]`：

```
2026-10-31 00:32:00.079 [iBootScheduler_Worker-2] [,] DEBUG ...
2026-10-31 00:35:12.101 [tomcat-handler-5] [aff3fd1f8c3ec7a42143f28bc6a54488,d83d07f767d1268b] INFO ...
```

- 请求线程带标识；
- 定时任务等无请求上下文的线程显示 `[,]`，**不伪造标识**。

### 9.4 查询链路

**首选：按标识查，不按时间窗查。**

网关会在响应头回显本次请求的 TraceID：

```bash
curl -s -D - -o /dev/null http://localhost:8088/api/user/list | grep -i x-trace-id
# X-Trace-Id: 112363636945bc0db5a37aa61c99e858
```

拿到标识后用脚本判断链路是否贯通：

```bash
# 判断链路里是否同时出现三个服务
bash scripts/regress/trace-chain.sh 112363636945bc0db5a37aa61c99e858 \
    --expect iboot-gateway,iboot-ai,iboot-admin
```

输出会给出服务分布与父子关系，退出码：`0` 齐全、`1` 缺服务或没有该标识、`2` 参数错误、
`3` 追踪后端不可用。追踪后端按批次导出，脚本默认在 10 秒内按标识轮询（`--wait` 可调），
其余应用日志里的 `[traceId,spanId]` 也可作为标识来源。

**辅助：人工浏览。** Grafana → Explore → Tempo，按 TraceID 查询或按服务名浏览。直接调
Tempo API 时注意时间窗边界：

```bash
# 最近 10 分钟内的链路（仅用于浏览，不作验证依据）
NOW=$(date +%s)
curl -s "http://localhost:3200/api/search?start=$((NOW-600))&end=$NOW&limit=20"

# 单条链路详情
curl -s "http://localhost:3200/api/traces/<traceId>"
```

> 时间窗查询的 `end` 是排他的。一次"查不到任何网关 span"的误判就是这么来的：请求时间戳
> `…911.58` 落在 `end=…911` 之外。

### 9.5 网关侧的 span

网关对经路由转发的请求**会**创建并导出服务端 span，这是框架能力，不需要自己埋点：

```
iboot-gateway  http get      (SERVER，根)   method=GET, http.url=/api/user/list
  └─ iboot-gateway  HTTP GET (CLIENT)       spring.cloud.gateway.route.id=admin
       └─ iboot-ai  http get /api/ai/...    （下游服务）
            └─ iboot-admin  http get /api/auth/scope
```

两点容易踩：

- 服务端 span 的低基数键 `uri` 是 `UNKNOWN`（网关没有 Spring MVC 那样的路径模板），路径只在
  高基数键 `http.url` 上，所以 span 名显示为 `http get` 而不是 `http get /api/user/list`；
- 不要自己再实现一个入口观测组件。框架已经在 `HttpWebHandlerAdapter` 里创建了服务端观测，
  重复创建会出现两条同级 span，污染父子结构与耗时统计。

`GatewayTracingTest` 用 `SimpleObservationRegistry` 断言"经网关的请求确实产生了服务端观测"，
它只读内存记录、不关心导出，因此能把"没创建"和"创建了但没导出"分开。

### 9.6 故障隔离与整体关闭

追踪后端停止时业务不受影响（实测请求仍返回 200），导出失败只在日志中记录。

需要彻底关闭追踪时设置 `IBOOT_TRACING_ENABLED=false`（落到 `management.tracing.export.enabled`）。
关闭后：不再产生 span，网关也不再回显 `X-Trace-Id`——那个标识在追踪后端查不到，回显它只会
把人引向错误方向。转发行为不变。

`GatewayTracingDisabledTest` 覆盖了这一点：关闭追踪时请求照常返回，且响应头中不含 `X-Trace-Id`。

## 10. 共享内核

### 10.1 模块与依赖

`iboot-kernel` 承载所有 HTTP 服务共用的三样东西：统一响应与异常处理、资源服务器鉴权、操作日志。

```xml
<dependency>
    <groupId>com.iboot</groupId>
    <artifactId>iboot-kernel</artifactId>
</dependency>
```

版本由父 POM 的 `dependencyManagement` 统一管理，各服务不需要写版本号。

| 包 | 内容 |
|---|---|
| `com.iboot.kernel.web` | `Result` / `PageResult` / `BusinessException` / `GlobalExceptionHandler` / `I18nUtil` |
| `com.iboot.kernel.security` | `JwtTokenUtil`、`JwtAuthenticationFilter`、`SecurityUtils`、白名单、`JwtSecurityConfig`、401/403 处理器 |
| `com.iboot.kernel.logging` | `@Log`、`LogAspect` 与 `sys_operate_log` 持久化链路 |

### 10.2 自动配置：不需要改启动类

宿主的组件扫描（通常是 `com.iboot.admin`、`com.iboot.file`）覆盖不到 `com.iboot.kernel`，内核组件全部通过自动配置注册：

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  com.iboot.kernel.web.KernelWebAutoConfiguration
  com.iboot.kernel.security.KernelSecurityAutoConfiguration
```

**这一点必须记住**：如果自动配置没被加载，应用照样启动、接口照样返回 200，只是鉴权与异常处理没有生效——这是静默的安全失效，不是启动失败。`KernelSecurityAutoConfigurationTest` 断言了过滤器确实进入过滤链。

内核提供的每个 Bean 都带 `@ConditionalOnMissingBean`：

- 定义了自有 `SecurityFilterChain` 的服务（`iboot-admin`、`iboot-ai`）保持原有过滤链，内核只提供过滤器与处理器；
- 新服务不写安全配置也能直接成为资源服务器。

### 10.3 白名单

白名单属于服务边界，由各服务自己声明：

```yaml
iboot:
  security:
    whitelist:
      - /actuator/**
      - /error
      - /v3/api-docs/**
```

内核只提供与业务无关的默认值（接口文档、`/actuator/**`、`/error`）。匹配语义：

- 以 `/**` 结尾 → 前缀匹配；
- 以扩展名通配符开头 → 后缀匹配（如 `/**/*.ico` 匹配任意 `.ico`）；
- 其余含 `*` → 通配符前的前缀匹配；
- 无通配符 → 精确匹配。

管理端与 AI 服务在 `application.yml` 里各自写全量列表，取值与迁移前的硬编码数组逐条一致。

### 10.4 全局异常处理的开关

内核默认注册 `GlobalExceptionHandler`（`Result` 信封 + 对应状态码）。如果服务已有自己的异常契约，用下面的配置关闭，避免既有响应结构被改写：

```yaml
iboot:
  kernel:
    exception-handler:
      enabled: false
```

`iboot-ai` 就是这种情形：它有自己的 `AiExceptionHandler`，关闭内核处理器后 OpenAPI 快照与迁移前完全一致。

### 10.5 401 / 403 约定

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 未携带令牌或被安全链拦截 | `401` | `Result` 信封，`message` 为「未授权，请先登录」 |
| 过滤器内异常（如 Redis 不可用） | `401` | `Result` 信封，`message` 为「认证失败，请重新登录」 |
| 已认证但无权限 | `403` | `Result` 信封，`message` 为「无权限访问」 |

内核不再依赖宿主的 `ObjectMapper`：响应体用 Jackson 3 的 `JsonMapper` 序列化，新服务不需要额外配置 Bean。

### 10.6 会话契约

鉴权的事实来源仍是共享 Redis，键与格式在 `Constants` 中定义：

| 键 | 内容 |
|---|---|
| `login_tokens:{token}` | 会话 Map：`userId`、`username`、`permissions` 等 |
| `online_tokens:{userId}` | 在线会话映射，用于单点互斥与在线用户列表 |

过滤器只读取与滑动续期，不签发令牌。续期时长取自 `jwt.session-timeout`（分钟）。

### 10.7 操作日志

内核只包含**写路径**：`@Log` 注解、`LogAspect`、异步 `OperateLogRecorder`（`JdbcTemplate` 插入 `sys_operate_log`，专用线程池 `operate-log-*`，写失败只告警）。

查询侧留在管理端：`OperateLogMapper.selectPage` 带 `@DataScope`，搬进内核会让多数服务携带一个静默失效的数据权限注解。

这是过渡形态：等 `iboot-monitor` 拆分时改为「发 CloudEvent → MQ → 落库」，届时删除内核中的直写实现。

> 没有数据源的上下文里记录器只告警一次并跳过写入，不会阻断启动——这让非 Web 测试切片不受影响。

### 11.2 四个不会报错、但会静默出错的隐式契约

前三项是拆分 `iboot-file` 时实际踩到的，第四项是拆分 `iboot-auth` 时补上的，
**漏掉任何一项，服务都能启动、健康检查也通过**：

1. **会话 Redis 序列化**：资源服务器读的登录会话由管理端以 Jackson 序列化写入。若宿主使用 Boot 默认的 JDK 序列化模板，读出来是 `null`，表现为「令牌有效但一直 401」。内核已提供同序列化的 `redisTemplate` 默认 Bean（`KernelRedisAutoConfiguration`），定义了自有模板的服务会覆盖它。
2. **CloudEvent 响应信封**：`/api/**` 的 `Result` 响应必须包成 `{type, source, data}`，前端与回归脚本都按 `data.data` 取值。实现是 `CloudEventResponseBodyAdvice`，它的 `basePackages` 必须指向本服务的 controller 包，否则响应结构会少一层。
3. **API 版本策略**：控制器上的 `version = "1"` 需要 `ApiVersionConfig` 提供 `ApiVersionStrategy`，否则启动直接失败（`API version specified, but no ApiVersionStrategy configured`）。
4. **`jwt.secret` 必须逐字一致**：签发方与校验方共用同一密钥与同一会话键前缀。密钥写成不同值（哪怕只差一个字符）时，表现为「**登录接口返回 200 并给出令牌，但后续所有请求都是 401**」，日志里只有一行验签失败，很难联想到配置。新增服务时不要图省事改写默认值，直接用 `${JWT_SECRET:iboot-admin-secret-key-for-jwt-token-generation-minimum-256-bits}`。

### 11.5 `iboot-auth` 的临时状态

服务端口 **8083**，承载 `/api/auth/login`、`/api/auth/logout`、`/api/auth/register`。

| 项 | 现状 | 退出条件 |
|---|---|---|
| 数据库 schema | 无自有 schema，数据源直连 `iboot_admin`；不启用 Flyway | `iboot-system` 拆分后改为经系统服务访问 |
| 写操作 | 仅三类：`sys_user` 最后登录信息、注册插入 `sys_user`、插入 `sys_login_log` | 同上，改为系统服务内部接口 |
| 会话 | 共享 Redis：`login_tokens:<jti>` 存会话快照，`online_token:<userId>` 指向当前 `jti`，`login_retry:*` 存失败计数 | 长期；令牌自包含后仍保留为撤销与在线名单 |
| 授权协议 | OAuth2 授权码 + PKCE，标准端点 `/oauth2/**`、`/.well-known/**`、`/connect/**`；登录页由本服务渲染 | 已完成 |
| 旧登录接口 | `/api/auth/login` 已移除；`/api/auth/logout`（撤销当前会话）与 `/api/auth/register`（自助注册）作为功能保留 | 已完成 |
| 授权记录 | 内存存储：重启后刷新令牌失效，需重新登录；已签发访问令牌的验签不受影响 | 需要跨重启续期时改为 Redis 存储 |
| `/api/auth/scope` | ❌ 不属本服务，仍在管理端；它返回数据权限范围，属系统域 | 随 `iboot-system` 迁走 |
| 登录指标 | `user_login_success` / `user_login_failed` / `user_online_count` 改由本服务上报，`application` 标签为 `iboot-auth` | 长期 |
| 管理端旧实现 | ✅ 已删除；网关把认证路径交给认证服务 | 已完成 |

**双栈过渡开关**：协议切换期间，资源服务同时接受两种令牌，由以下配置控制：

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `jwt.jwk-set-uri` | `http://localhost:8083/oauth2/jwks` | 认证服务公钥集地址。资源服务首次遇到自包含令牌时回源，之后本地缓存；认证服务短暂不可用不影响已缓存的验签 |
| `jwt.legacy-enabled` | `false` | 认证协议切换已完成，四个服务都关闭了旧令牌兼容；打开它只用于回滚演练 |

携带旧令牌的请求返回业务码 **`40101`**（令牌版本已过期），与普通认证失败（`401`）区分开——前端据此静默重新登录，而不是提示凭据错误。`/api/auth/login` 已随协议切换下线。

**一个容易被忽略的特性**：认证服务宕机时，**已登录用户不受影响**——资源服务器用已缓存的公钥验签，
只查共享 Redis 的撤销名单，不依赖认证服务在线；只有当用户尝试重新登录、或资源服务冷启动且公钥缓存为空时
才会失败。这条能力在协议切换后仍然保留。

服务端口 **8085**，承载 `/api/job/**`（定时任务管理与执行）与 `/api/monitor/backup/**`（数据备份与恢复演练）。
本变更只做「结构先行」：新服务上线并接管路由，管理端旧实现原样保留作为回退点。

| 项 | 现状 | 退出条件 |
|---|---|---|
| 数据库 schema | ✅ 独立 `iboot_job`，15 张表由本服务 Flyway 管理：`QRTZ_*`（11）、`sys_job`、`sys_job_log`、`db_backup_record`、`db_restore_record` | 数据搬迁与源表清理在 `remove-job-from-admin` 中完成 |
| 跨 schema 只读 | `SysConfigReader` 读 `iboot_admin.sys_config`（存储类型 `sys.file.storageType`）；`DictLabelLookup` 读 `iboot_admin.sys_dict_data`（Excel 导出的字典标签） | `iboot-system` 拆分后改为调用系统服务 |
| 数据权限 | 任务列表带 `@DataScope`：带调用者令牌请求 `http://iboot-admin/api/auth/scope`（服务名寻址），本地缓存 60 秒，**失败关闭** | 管理端提供稳定 scope 契约后切到 `iboot-system` |
| 调度 | Quartz **集群模式**（`isClustered: true`、`instanceId: AUTO`）。启动时只做增量对账，不再 `scheduler.clear()`——集群下清空会抹掉其它实例正在执行的任务 | 长期 |
| 备份执行 | 经 `docker exec` 调用 `iboot-mysql` 容器内的 `mysqldump` / `mysql`，产物经存储 SPI 加密落盘；启用时启动阶段检查密钥、存储与命令行可达 | 阶段 3 容器化后改为直连或自带客户端 |
| 管理端旧实现 | ✅ 保留，参与编译与测试；**两侧数据源不同**（`iboot_job` vs `iboot_admin`），因此过渡期两边的任务列表会不一致——路由决定用户看到哪一份 | `remove-job-from-admin` 搬迁数据后删除 |
| 网关路由 | 两条**路径级**路由：`/api/monitor/backup/**` 与 `/api/job/**`，order 28，排在 admin 兜底之前 | 长期；monitor 拆分后把 `/api/monitor/**` 排在本条之后 |

**为什么路由是路径级而不是前缀级**：备份的路径挂在 `/api/monitor` 下，而 `monitor` 尚未拆分，
其余 `/api/monitor/**` 仍归管理端。登记成 `/api/monitor` 会让 `path-conservation` 永远无法达到 `done`，
这与 `extract-auth-service` 时 `/api/auth/scope` 的处理同理。

**Quartz 集群的注意事项**：

- 多个实例必须共用同一份 `QRTZ_*` 存储与同一个 `scheduler-name`（本服务为 `iBootScheduler`）；
- 节点之间的时钟偏移会影响触发精度，本地验证时用同一台机器即可；
- `QRTZ_LOCKS` 由 Quartz 自行维护，不要手工增删行；
- **故障语义是至少一次**：某个实例被强杀时，Quartz 会把该节点执行中的触发器恢复并重跑一次，
  故障瞬间可能出现两条同秒执行记录。任务实现必须幂等；实测 `sampleTask` 每 10 秒触发、
  双实例运行时正常时段每个时刻只有一条，强杀后出现一次重跑；
- 回退到单实例：把 `org.quartz.jobStore.isClustered` 改为 `false` 并重启即可，表结构无需变更。

**回滚**：把网关两条路由改回指向管理端即可，业务代码与数据库都不用动。

## 12. 拆分专用的三个回归脚本

`regress.sh` 的顺序是「快照 → 路径守恒 → 路由覆盖 → 冒烟 → 权限矩阵」。

### 12.1 `path-conservation.sh`

```bash
bash scripts/regress/path-conservation.sh
```

比较**本次导出**与**基线**的路径并集：并集必须完全相同；消失或新出现的路径必须能由 `migrations.txt` 解释。同时校验登记的迁移确实落地。

`migrations.txt` 每行四列：

```
<路径前缀> <源服务> <目标服务> <transitional|done>
```

- 服务名用快照名（`admin` / `ai` / `file` / `auth`），不是 Nacos 服务名；
- `transitional`：绞杀者过渡期，源服务仍保留旧实现，只要求目标服务已有该前缀；
- `done`：旧实现已删除，源服务再出现该前缀即失败。

`remove-file-from-admin` 把旧实现删掉后，把这条登记改成 `done`。

**登记粒度要按「真正搬走的边界」来定**。`extract-auth-service` 只搬了登录、登出与注册，
`GET /api/auth/scope` 仍留在管理端，所以不能登记 `/api/auth` 前缀——那样永远达不到 `done`：

```
/api/auth/login    admin auth done
/api/auth/logout   admin auth done
/api/auth/register admin auth done
```

对应的网关路由也必须是逐条路径，而不是 `/api/auth/**`，否则 scope 会被错误地转发到认证服务。

### 12.2 `equivalence.sh`

```bash
bash scripts/regress/equivalence.sh --record   # 迁移前，从 REG_BASE（默认 8080）录制
REG_RECORD_BASE=http://localhost:8082 \
  bash scripts/regress/equivalence.sh --record # 旧实现删除后，改从文件服务录制（登录仍走 REG_BASE）
bash scripts/regress/equivalence.sh --verify   # 迁移后，经 REG_GATEWAY（默认 8088）重放
```

覆盖四条只读请求：`list`、`{id}`、`download-url/{id}`、`export`。归一化规则：

- 业务 `timestamp` 与 CloudEvent 信封的 `id` / `time` 置为占位符；
- 预签名下载地址的查询串掩掉（带签名与过期时间）；
- Excel 只对工作表内容取哈希，忽略文档属性里的生成时间。

**适用范围仅限只读请求**：写操作的响应含自增 ID 与时间戳，由冒烟覆盖。录制与校验之间不能有写入，否则数据变化会被当成差异。

### 12.3 冒烟与矩阵的变化

- 冒烟的「文件上传与下载」整段改走网关，覆盖上传 → 列表 → 下载地址 → 下载内容 → 删除五步；
- 权限矩阵新增三条文件用例：无 `file:list` 时拒绝、有 `file:list` 时允许、仅本人数据范围下看不到他人文件（超管 7 个 vs 受限 0 个）。
